## 1. Authority and problem

GAP-124 (`docs/architecture/BLUEPRINT_GAPS.md`) is **PARTIAL**. E4-V1 replaced DataView's "Loading" text with the shared spinner icon, `aria-hidden`, plus visually hidden "Loading" text in a `role="status"` region. Two residuals remain:

1. **Motion.** The spinner never rotates. Angular and Vue spinner icons emit `u-icon-spin`, but no stylesheet defines it. PrimeNG and PrimeVue define the rotation in the icon's own `BaseIconStyle`. Affected consumers: Button and DataView in both frameworks.
2. **Contrast.** The DataView loading icon is drawn in `mask.color` (`surface.200`, `#e2e8f0`) on the light-scheme mask composited over white (`#999999`): **2.31:1**, below WCAG 2.2 SC 1.4.11's 3:1. No WCAG exception is supported (proposal §2.2).

Binding user rulings: D-124-1 (the spin is outside the GAP-098 boundary and stays icon-scoped), D-124-4 (A-1, a shared class-scoped rule), D-124-5 (React out only if provably unchanged), D-124-6 (RM-1, static under reduced motion), D-124-7 (B-2, a DataView-scoped dark color from existing tokens).

## 5. Design — item A (motion)

### 5.1 Rule

A new module in `@ultimate/uix-styled`, next to `stylesheet/hidden-accessible.ts`, exports a reserved key `ICON_SPIN_KEY = "u-icon-spin"`, the CSS text, and `registerIconSpin(sheet)`. Its CSS is exactly:

```css
.u-icon-spin {
  animation: u-icon-spin 2s infinite linear;
}

@keyframes u-icon-spin {
  0% {
    transform: rotate(0deg);
  }
  100% {
    transform: rotate(359deg);
  }
}

@media (prefers-reduced-motion: reduce) {
  .u-icon-spin {
    animation: none;
  }
}
```

- **Source:** PrimeNG 21.1.9 `icons/baseicon/style/baseiconstyle.ts` and PrimeVue 4.5.5 `packages/icons/src/baseicon/style/BaseIconStyle.js` (identical `.p-icon-spin` rules), renamed to the `u-` prefix.
- **Recorded differences from Prime:**
  - the `-webkit-` duplicates are omitted (supported engines use the unprefixed properties);
  - the reduced-motion block is Ultimate-only (D-124-6).
- **Scope:** the only selector is the class `.u-icon-spin`. No element, universal or attribute selector.

### 5.2 Registration

`registerIconSpin(sheet)` follows the `registerHiddenAccessible` contract (GAP-074): it adds the CSS once per sheet under `ICON_SPIN_KEY`, guarded by `has()`. It is a separate function. The spin CSS is **not** appended to `hiddenAccessibleCss`.

| Core         | Call site                                                                      | Effect                                 |
| ------------ | ------------------------------------------------------------------------------ | -------------------------------------- |
| `ng-core`    | `UBaseComponent.ngOnInit`, beside `registerHiddenAccessible(sheet)`            | Per document, including SSR (GAP-078). |
| `vue-core`   | `registerComponentStyle`, beside `registerHiddenAccessible(vueCoreStyleSheet)` | Once per `vueCoreStyleSheet`.          |
| `react-core` | **Not called.**                                                                | No change.                             |

Button and DataView both extend the base component in each framework, so the rule is present whenever either renders.

**Known limitations (accepted under SR-2; recorded in `MIGRATION.md`, not fixed):**

- **KL-1, standalone icon:** an Angular or Vue Ultimate icon rendered with `spin` does not rotate unless an Angular or Vue Ultimate component has already registered the rule in that document.
- **KL-2, mixed-framework document:** the rule is a document-level class selector. In a document that renders an Angular or Vue Ultimate component, a React Ultimate spinner carrying `u-icon-spin` will also rotate, and will stop rotating under reduced motion.

### 5.3 React scope (D-124-5 condition)

**React-only documents are unchanged; mixed-framework documents can be affected (KL-2).** Verified at `b2bd892`:

- each core owns its own sheet;
- `@ultimate/uix-styled` writes CSS only when a core calls a helper;
- `react-core` will not call `registerIconSpin`.

Four checks prove the React-only claim (R-AC1..R-AC4, §9). If any check fails, implementation stops and the scope question returns to the user for review.

**React file boundary:**

- **Must not change:** React production source (`packages/react/src/**` and `packages/react-core/src/**`, excluding `*.spec.ts(x)`), production styles, and visual baselines (`packages/react/e2e/**-snapshots/**`).
- **Allowed:**
  - new dedicated GAP-124 test files that prove React-only documents are unchanged: `packages/react/src/button/gap-124-react-unchanged.spec.tsx` and `packages/react/e2e/gap-124-react-unchanged.spec.ts`;
  - their provenance entries in `docs/architecture/provenance/react.json`.
- **Unchanged by this boundary:** the mixed-framework limitation KL-2.

### 5.4 Reduced motion (RM-1)

Under `prefers-reduced-motion: reduce`, the computed animation is `none` and the icon stays at its normal size, position and opacity. Under the default setting (`no-preference`), the icon rotates continuously. In both cases the loading state remains visible through the mask and the static spinner glyph, and is announced through the unchanged live region. No substitute animation is added.

## 6. Design — item B (contrast)

### 6.1 Color

Under `.u-data-view > [role="status"]`, the DataView loading icon's `<svg>` takes `color: dt('text.hover.color')`. The icon path uses `fill="currentColor"`, so the fill follows. The mask background and the region's own `color` are unchanged.

Resolved values: the light scheme maps `surface` to `slate`, and the dark scheme maps it to `zinc` (`packages/themes/src/presets/aura/base.ts`).

| Token                                   | Light                           | Dark                           |
| --------------------------------------- | ------------------------------- | ------------------------------ |
| **`text.hover.color` (selected, SR-1)** | `surface.800` = slate `#1e293b` | `surface.0` = `#ffffff`        |
| `text.color` (rejected)                 | `surface.700` = slate `#334155` | `surface.0` = `#ffffff`        |
| `mask.color` (current, pre-change)      | `surface.200` = slate `#e2e8f0` | `surface.200` = zinc `#e4e4e7` |
| `mask.background` (unchanged)           | `rgba(0,0,0,0.4)`               | `rgba(0,0,0,0.6)`              |

- **Why `text.hover.color` (approved, SR-1):** it is an existing semantic token that is dark in the light scheme and light in the dark scheme, and it has a wider margin than `text.color` over non-white light surfaces (§6.4).
- **Static use of a "hover" name:** this is intentional. A comment in `g3e-port.mjs`, at the rule, says so and cites this Spec.
- **New token:** not needed. Every required condition in §6.4 passes with the existing token.

### 6.2 Generator placement

The rule is added to `g3e-port.mjs` for both frameworks' `dataview` output as an Ultimate-authored rule. The generator records its source as "none (Ultimate addition, GAP-124 B-2)" and gives the contrast reason, in the same form as the existing `BASE_SOURCES` difference records. The generated `packages/ng/src/data-view/data-view-style.ts` and `packages/vue/src/data-view/data-view-style.ts` are then regenerated. The exact role category (base or runtime list) is a plan-level choice; the generator's existing fixture checks must stay green.

### 6.3 Visual fidelity

In the light scheme the spinner becomes dark slate on the grey mask, while Prime's is light. In the dark scheme the icon becomes white instead of `surface.200`. This is a deliberate accessibility divergence, recorded in §8.

### 6.4 Contrast coverage — declared background conditions

The contrast guarantee is **not universal**. It covers only the declared conditions below: the mask composited over a **uniform** underlying surface filling the DataView root (`.u-data-view` is `position: relative`, and the status mask covers its padding box).

- **Underlying surfaces:** DataView's default `content.background` is `surface.0` (light) and `surface.900` (dark). The other required surfaces are representative non-white content the mask can sit over.
- **Expected values:** calculated from token values (sRGB relative luminance) as the contrast of the specified icon color against the specified mask composite. That is the quantity W3C defines: it evaluates contrast with the colors "obtained from the user agent, or the underlying markup and stylesheets", with anti-aliasing turned off. The §10 measurement reproduces it from rendered pixels by excluding edge pixels, so the expected rendered values equal these up to 8-bit compositing rounding: each rendered value must lie in its rounding range (§10, B-AC6).

**Required conditions** (each asserted separately at ≥ 3:1, both frameworks):

| ID   | Scheme | Underlying surface      | Why it is declared                         | Mask composite | Expected, new (`text.hover.color`) | Pre-change (`mask.color`) |
| ---- | ------ | ----------------------- | ------------------------------------------ | -------------- | ---------------------------------- | ------------------------- |
| C-L1 | Light  | `surface.0` `#ffffff`   | DataView default `content.background`      | `#999999`      | 5.13                               | 2.31                      |
| C-L2 | Light  | `surface.100` `#f1f5f9` | `content.hover.background`                 | `#919395`      | 4.74                               | 2.50                      |
| C-L3 | Light  | `surface.200` `#e2e8f0` | light grey content; `content.border.color` | `#888b90`      | 4.28                               | 2.77                      |
| C-L4 | Light  | `surface.300` `#cbd5e1` | lightest mid-grey content still covered    | `#7a8087`      | 3.67                               | 3.24                      |

| C-D1 | Dark   | `surface.900` `#18181b` | DataView default `content.background`      | `#0a0a0b`      | 19.79                              | 15.60                     |
| C-D2 | Dark   | `surface.800` `#27272a` | `content.hover.background`                 | `#101011`      | 19.02                              | 14.99                     |

**Not covered — documented conditions where 3:1 is not met** (light scheme; the new dark icon over a darkened mid-tone):

| ID   | Underlying surface      | Mask composite | Expected, new | Pre-change |
| ---- | ----------------------- | -------------- | ------------- | ---------- |
| N-L1 | `surface.400` `#94a3b8` | `#59626e`      | **2.37**      | 5.01       |
| N-L2 | `surface.500` `#64748b` | `#3c4653`      | **1.53**      | 7.77       |
| N-L3 | `primary.500` `#10b981` | `#0a6f4d`      | **2.36**      | 5.02       |

- **Light-scheme boundary:** for a neutral grey underlying surface, the new icon meets 3:1 only when the surface is at least as light as `#bebebe`.
- **Darker light-scheme content:** saturated or darker content under the mask (images, primary-colored blocks, text) can fall below 3:1. No single icon color meets 3:1 over every surface, because the light mask spans both light and dark composites.
- **How these are recorded:** the measurement reports these as annotations, not assertions (§10). `MIGRATION.md` and the Parity Playbook note record this limitation as KL-3.
- **Dark scheme:** every declared dark condition passes. The darkest-possible composite is black, and the brightest, over white, is `#666666`, which gives 5.74.
- **KL-4, thin stroke (recorded limitation, not fixed):** the spinner arc is about 1.17 CSS px wide at the rendered 14 CSS px size. At 1× device pixel ratio few or no pixels are fully covered, so anti-aliasing renders the stroke fainter than its specified color. W3C notes this effect and recommends, as best practice and not as a requirement, avoiding particularly thin lines. The guarantee in this section is for the specified colors (fully covered stroke pixels). The rendered, anti-aliased contrast is measured and reported, not asserted (§10, layer L2). Changing the icon geometry is out of scope (Prime's spinner path is ported verbatim).

If any **required** condition measures below 3:1 in the browser, implementation stops and the color decision returns to the user before approval is requested.

## 10. Contrast measurement (B-AC1, B-AC2, B-AC6, B-AC7)

**Why the method changed (revision 4).** Revision 2 took, for each ring sample, the icon pixel with the greatest contrast. One fully covered pixel could then carry a pass even if the rest of the stroke rendered fainter. The method below measures every fully covered stroke pixel and uses the minimum.

**Fixture:** the DataView `loading` story (`data-dataview--loading`) in each framework. It already exists in Angular. Vue gets a new test-only `Loading` story (A1-1); it is not part of the G3-E visual or accessibility suites, and the Vue `no-prime-reference` parity record is unchanged.

**Setup, for each condition:**

1. Emulate the condition's scheme with `page.emulateMedia({ colorScheme, reducedMotion: 'reduce' })`. Ultimate's default `darkModeSelector` is `system`. Reduced motion keeps the glyph static.
2. Set the declared underlying surface as an inline `background-color` on the `.u-data-view` root.
3. Set `visibility: hidden` on the root's other children (list, grid, paginator), so the area under the mask is that uniform surface.
4. These test-only inline styles change no component code.

**Layer L1 — specified-color contrast, asserted (B-AC1, B-AC6, B-AC7).** Run at `deviceScaleFactor: 4`, where the 1.17 CSS px stroke spans about 4.7 device pixels and has a fully covered interior.

1. **Clip:** the icon's bounding box plus a 6 CSS px margin. Every capture uses the same clip, with `animations: 'disabled'`.
2. **Four captures** of that clip, changing only the icon's inline style:
   - **N:** as rendered;
   - **H:** icon `visibility: hidden`;
   - **K:** icon `color: #000`;
   - **W:** icon `color: #fff`.
     The icon path is `fill="currentColor"`, so K and W change only the fill.
3. **Coverage per pixel:** `α = mean over R, G, B of (W − K) / 255`. Source-over blending gives `pixel = α·fill + (1 − α)·background` per channel, so `W − K = 255·α` regardless of the background. This measures anti-aliasing coverage directly from the rendering.
4. **Icon pixels:** pixels with `α ≥ 0.05` (ink). **Fully covered pixels (core):** pixels where `W − K ≥ 254` on **every** channel, i.e. full coverage within 8-bit rounding. Their color in N is the rendered fill with no edge blending. A looser threshold, for example `α ≥ 0.95`, would admit slightly blended edge pixels. It would lower the minimum (simulated: 4.79 instead of 5.13 on C-L1) and break the ±2 color guard on a correct implementation.
5. **Adjacent colors:** every pixel of H, which is the mask with the icon removed, under and around the icon.
6. **L1 value:** the **minimum** contrast over all pairs (core pixel in N, pixel in H). This is the worst case between any fully covered stroke pixel and any adjacent mask pixel.
7. **Validity guards (B-AC7):**
   - core count ≥ 100 and ≥ 25% of ink pixels;
   - every core pixel within ±2 per channel of the icon's computed `color`.
     A failed guard throws, and the test fails.
8. **Assertions:**
   - required conditions: `expect.soft(L1 ≥ 3)` per condition, plus `expect.soft(L1 within its rounding range)` per condition;
   - N-L1..N-L3: the tolerance assertion plus an annotation, with no ≥ 3 assertion;
   - negative control (C-L1 with the icon forced to `mask.color`): `L1 < 3` and `L1` within its rounding range (fill `#e2e8f0`, about [2.24, 2.35]).

**Layer L2 — rendered anti-aliased contrast, reported only (KL-4).** For C-L1 and C-D1, at `deviceScaleFactor` 1 and 2, the same captures are taken, without the validity guards. These are recorded as annotations:

- the core and ink pixel counts;
- the median contrast of pixels with `α ≥ 0.5` (in N) against the least-contrasting H pixel.

They are not asserted, because W3C evaluates contrast with anti-aliasing turned off. They make the thin-stroke effect visible in the verification record instead of hiding it.

**Expected values.**

- **L1:** the §6.4 values are the nominal expectations. By construction, core pixels are the specified fill and H is the specified mask composite, so only 8-bit compositing rounding separates them. The test computes, per condition, the **rounding range**: the minimum and maximum WCAG ratio over every combination of (a) the mask composite with each channel rounded down or up (`floor(c·(1 − α))` or `floor(c·(1 − α)) + 1`) and (b) the icon fill with each channel offset by −2, 0 or +2 (the B-AC7 guard), with a 0.005 floating-point margin. Examples: C-L1 [5.00, 5.34], C-L4 [3.53, 3.77], C-D1 [19.46, 19.90], C-D2 [18.70, 19.16]. Every range for a required condition stays ≥ 3.
- **Out-of-tolerance results:** if a browser engine's results differ by more than that, the test fails and the stop rule applies.
- **L2:** no expected values; it is recorded for information.

**Why this method is defensible:**

- **The quantity:** it measures what W3C defines (the specified colors, without anti-aliasing), but from actual rendered pixels rather than from stylesheets.
- **The pixels counted:** it uses every fully covered pixel instead of one.
- **Anti-aliasing:** it identifies edge pixels from measured coverage rather than guessing.
- **Validity:** it fails closed when the rendering gives too few fully covered pixels to judge.

**What it does not establish:** perceived legibility of a thin stroke at 1× pixel ratio (KL-4). L2 reports that; it is not part of the 3:1 guarantee.

## 12. Risks

- **Underlying content.** Consumer content beneath the mask varies. The guarantee covers only the declared conditions in §6.4. Darker or saturated light-scheme content falls below 3:1 (N-L1..N-L3, KL-3); this is documented, not claimed as conformant.
- **Measurement.** The coverage calculation assumes source-over blending in the captured color space. That is the default for SVG fills in all three engines. The per-condition rounding range on L1 and the validity guards detect a violation, for example color management in a capture, and fail instead of passing.
- **Theme variables.** `dt('text.hover.color')` must resolve inside the DataView module. The plan verifies that the semantic variable is registered, as `mask.*` already is.

## 15. Final Review correction (revision 4, 2026-10-11)

- **Finding (user):** the revision-2 measurement chose the single most-contrasting icon pixel per ring sample, which can overstate the rendered contrast of the stroke as a whole.
- **Correction:**
  - §10 now uses a coverage map from differential captures (K/W), asserts the minimum over all fully covered pixels against all adjacent mask pixels (B-AC1), and checks every value against its §6.4 expectation within ±0.10 (B-AC6).
  - It fails closed on invalid measurements (B-AC7).
  - The rendered anti-aliased contrast is reported as layer L2.
- **Threshold check (design-time arithmetic, scratch only, no repository code):** a simulation of source-over blending with 8-bit rounding confirmed:
  - with the strict full-coverage threshold, L1 equals the analytic value: C-L1 5.135, the negative control 2.311, C-D1 19.79, with core deviation 0;
  - a 1×-like thin stroke fails closed (3 core of 153 ink pixels);
  - an `α ≥ 0.95` threshold would wrongly lower the value to 4.79.
- **Limitation made explicit:** KL-4 (thin stroke, §6.4). The 3:1 guarantee is for the specified colors, following W3C's measurement guidance.
- **Unchanged:** the per-condition assertions, the negative control, the not-covered annotations, the stop rule, and the item A/B rollback boundaries.

## 16. Amendment A2 — L1 tolerance (user ruling, 2026-10-11, during Task 8)

- **Finding (Task 8 stop rule, B-AC6):** with the fixed ±0.10 tolerance, 50 of 54 runs passed. C-D1 and C-D2 were outside it in Firefox (+0.114, +0.138) and WebKit (−0.168, −0.164); Chromium was within. No required condition was below 3:1 (lowest 3.67, C-L4), no validity guard failed, and the computed icon color matched in all six projects.
- **Cause:** near black, one 8-bit step in the mask composite moves the ratio by about 0.11–0.17. Chromium and Firefox composite `rgba(0,0,0,0.6)` over `#18181b` to `9,9,10`; WebKit gives `10,10,11`. A fixed ±0.10 cannot hold for the ~19:1 conditions.
- **Ruling (user):** replace ±0.10 with the per-condition rounding range defined in B-AC6 and §10. Every observed value lies inside its range, and the range still fails on a wrong color, color management, or a broken method. The ≥ 3:1 assertions, the validity guards, the negative control and the stop rules are unchanged.
