## 5. Specification-Level Decisions (binding, made here)

### C1 — Changesets workflow shape

**Decision:** the release workflow is the standard three-step Changesets flow, wired as npm scripts (new, added by this track's future Implementation Plan — not created by this Specification document itself):
1. **`changeset` (add):** a contributor run, `npx changeset add`, authoring one `.changeset/<random-name>.md` file per user-facing change, naming the affected package(s) and bump type (`patch`/`minor`/`major`).
2. **`changeset version` (version bump + changelog):** consumes all pending `.changeset/*.md` files, bumps each affected package's `package.json` version per SemVer + the collected bump types, regenerates `CHANGELOG.md` entries via the configured `@changesets/changelog-git` generator, and deletes the consumed changeset files. This step is run by a release automation step (CI-triggered, per C3), not manually by each contributor.
3. **`changeset publish` (publish):** publishes each version-bumped package whose version does not yet exist on the configured registry. Requires real registry authentication (an `NPM_TOKEN`-shaped secret) that does not currently exist in this repository's configuration — not invented here, see C4/§7's external-only note.

**Rationale:** this is exactly `@changesets/cli`'s own documented, standard flow (confirmed via its installed README and `--help` output this session) — no custom wrapper or alternative flow is invented. It matches `.changeset/config.json`'s existing settings (`commit: false` means step 2 does not auto-commit; a release workflow must handle that itself — see C3).

### C2 — Changelog generator reconciliation

**Decision:** Track D's Specification (D2) already identified that the installed `@changesets/changelog-git@0.2.1` generator produces flat, uncategorized bullet lines, not the five-category Keep-a-Changelog convention CHANGELOG.md's header documents as a manual curation layer. Track D explicitly deferred *resolving* this mismatch to Track C (D2: "reconciling this human-facing convention with the generator's real flat-bullet output... is a Track C decision"). **This Specification's decision: do not change the generator.** Keep `@changesets/changelog-git` exactly as configured. The five-category convention remains a manual, human-facing curation step applied at release-PR-review time (a human editing the generated `CHANGELOG.md` diff before merging the release PR, sorting flat bullets under the appropriate category headers) — not automated. **Rationale:** switching to `@changesets/changelog-github` (the other commonly-available option) requires a GitHub token with API access this repository does not have configured, and no evidence anywhere in the repository suggests categorized automatic output is a hard requirement rather than a nice-to-have; changing the generator is exactly the kind of "redesigning the existing Changesets mechanism" the task's explicit non-goals forbid without new evidence forcing it, and no such evidence was found.

### C3 — Release automation trigger and flow

**Decision:** release automation follows the standard "Changesets GitHub Action" pattern (`changesets/action`, the mechanism the official Changesets project itself documents) at the *contract* level only: on every merge to `main` that includes pending `.changeset/*.md` files, a release workflow either (a) opens/updates a "Version Packages" PR (running `changeset version`, committing the result, but not yet publishing), or (b) if such a PR already exists and was itself just merged, runs `changeset publish` against the real registry. This is the two-phase pattern that keeps version bumps human-reviewable before anything actually publishes. **This Specification does not create `.github/workflows/release.yml`, does not specify its exact job/step composition, and does not choose between the consolidated `changesets/action@v1` entrypoint versus its individual sub-actions (`changesets/action/version`, `changesets/action/publish`)** — that composition choice is Implementation Plan territory, deliberately left open here because it interacts with an environment-approval/OIDC constraint this Specification's research surfaced (see C5) that the Implementation Plan must account for, not this document.

Six distinct concerns, kept explicitly separate per this review's finding that the original C3/R4 draft conflated them:

1. **Creation of changesets** — contributor-run, local, `changeset add`, no CI involvement (R1).
2. **Version-package/release PR generation** — CI-run, `changeset version` + commit + PR open/update, gated on pending changesets existing (R4 item 1).
3. **Merging the release PR** — a human action (a repository maintainer approving/merging the "Version Packages" PR) — this Specification does not, and cannot, automate human PR approval.
4. **Publishing** — CI-run, `changeset publish`, gated on the release PR having just been merged (R4 item 2), and gated on Track B's quality gates having already passed on that commit (R4 item 3).
5. **Provenance/attestation generation** — a property of *how* publishing authenticates (C5), not a separate step — either automatic (if OIDC trusted publishing is used) or not generated at all (if token-based publishing is used, per C5's finding that this repository's pinned tooling cannot use the flag-based alternative either).
6. **Required CI gates and human approval points** — Track B's full `ci` job must have passed on the release commit before `changeset publish` runs (fail-closed, §9); the release PR merge (item 3) is the one and only human approval point in this flow — no additional manual gate is introduced beyond it.

**Rationale:** this is the standard, widely-used Changesets release pattern (not a novel design), keeping with this repository's already-established preference (Track B, Track A) for standard/official tooling over custom automation. No genuine alternative flow shape was found or evaluated.

### C4 — Publish trigger, registry target, and package access (decided)

**Decision:** the publish contract, as a specification-level contract (not yet a working credential or workflow). Three distinct concerns, kept explicitly separate per this pass's own review instruction:

1. **Package visibility/access level — DECIDED, binding project decision:** `@ultimate/*` packages are **private/restricted npm packages**, permanently, not merely as an unconfigured default awaiting a later choice. `.changeset/config.json`'s existing `access: "restricted"` is **consistent with, and correct for, this decision** — no configuration change is required or made. This is not an implementation-plan detail; it is settled project intent, restated here so the publish contract is unambiguous about which of npm's two access levels governs every one of the 17 packages in §8.
2. **Target registry:** the public npm registry (`https://registry.npmjs.org`, confirmed as this machine's configured default). **Distinguishing this from package access level (item 1):** "public registry" describes *where* packages are hosted (there is no private/self-hosted registry referenced anywhere in repository evidence, and none is invented here); "restricted access" (item 1) describes *who can install* a package hosted there. A restricted/private package on the public npm registry is a completely ordinary, common configuration — the registry itself does not need to be private for the package to be. No repository evidence suggests a private registry (e.g., a self-hosted Verdaccio instance or GitHub Packages) is needed or intended; this Specification does not invent one.
3. **Registry authentication — token-based, per C5:** requires an `NPM_TOKEN`-shaped repository secret (GitHub Actions secret) granting publish rights to the `@ultimate` npm org/scope. **No such secret, npm org, or token currently exists in any repository-visible configuration** (confirmed: no `.github/workflows/*.yml` references any `NPM_TOKEN`-shaped secret name; this is unverifiable from repository content since GitHub Actions secrets are never stored in the repository itself by design). This Specification does not invent one — it documents the requirement as a precondition for actually exercising `changeset publish`, distinct from being able to define the workflow shape (C3) without it. **This authentication requirement is independent of, and does not itself depend on, the package's restricted/public access level (item 1)** — a restricted package still needs a valid, authorized token to publish, exactly as a public one would; access level governs who can *install* the result, not how the *publisher* authenticates.

**Registry authentication vs. publish-time provenance (binding distinction, restated for this section since the two were previously conflated in this Specification's original draft):** authentication (item 3, "can this workflow publish at all") and provenance (C5/R6, "can a consumer cryptographically verify how this package was built") are two unrelated concerns that happen to both involve the registry. A restricted package can authenticate and publish successfully (item 3) while still having zero provenance attestation (C5) — these are not the same requirement, and satisfying one says nothing about the other.

### C5 — Provenance/attestation mechanism (corrected; provenance is structurally foreclosed by the project's own access decision, independent of tooling)

**This section was substantively wrong in this Specification's original draft and has now been corrected twice: once (first Spec Review pass) after direct verification against the installed tooling's own source code, and again (this pass) after the project's own binding restricted/private access decision (C4 item 1) was found to add a second, independent reason provenance cannot be delivered — not merely a tooling-version gap, but a structural incompatibility with the decision itself.**

**What the original draft claimed:** `changeset publish` forwards a `--provenance` flag to `npm publish`, combined with an `NPM_TOKEN` secret and `id-token: write` OIDC permission, all at once.

**What direct verification found, across both Spec Review passes, in order:**

1. **`@changesets/cli@2.31.1` (the version installed in this repository) has zero code path referencing "provenance" anywhere in its distributed source.** Direct inspection of `node_modules/.pnpm/@changesets+cli@2.31.1/node_modules/@changesets/cli/dist/changesets-cli.cjs.js` shows the `publish` command's `publishFlags` array is constructed from exactly: `--access`, `--tag`, `--no-git-checks`, `--json`, `--otp` — no mechanism exists for a `--provenance` flag (or any other npm/pnpm CLI flag) to pass through `changeset publish` to the underlying `npm publish`/`pnpm publish` invocation. This matches a real, currently-open-at-time-of-writing upstream feature request, [`changesets/changesets#1152`](https://github.com/changesets/changesets/issues/1152) ("Add support for publishing with provenance"), confirming this is a known, unresolved gap in the tool itself, not a misconfiguration on this repository's part.
2. **npm's own current documentation (`docs.npmjs.com/trusted-publishers`, `docs.npmjs.com/generating-provenance-statements`, fetched directly, and re-fetched with more targeted verbatim-quote extraction this pass) describes two distinct, non-combinable authentication models, not one combined mechanism:**
   - **Model A — token-based, explicit `--provenance` flag.** Uses a long-lived `NPM_TOKEN`. Requires `npm publish --provenance` to be passed explicitly (npm CLI, not pnpm — see finding 3). Requires `package.json`'s `repository` field to match a **public** repository the publish runs from. **On first publish specifically, requires the publish call itself to pass `--access public`** (npm's own documented example: `npm publish --provenance --access public`) — a direct, literal requirement that the *individual publish invocation* declare public access, which cannot be honestly satisfied for a package the project has decided must remain restricted (C4 item 1). Does **not** need `id-token: write`.
   - **Model B — OIDC Trusted Publishing.** No `NPM_TOKEN` at all — npm CLI auto-detects the CI-provided OIDC identity. Requires `permissions: { id-token: write }` in the workflow, npm CLI ≥ 11.5.1. Trusted Publishing's *authentication* mechanism itself is not documented as restricted to public packages — but **automatic provenance generation under this model is.** npm's own documentation lists the exact conditions for automatic provenance as: "Publishing via trusted publishing (OIDC)," **"Publishing from a public repository,"** and **"Publishing a public package"** — all three, verbatim, as separate, named conditions (re-fetched and quoted directly this pass, not paraphrased). It further states: "Provenance generation is not supported for private repositories, even when publishing public packages." **A permanently-restricted package (C4 item 1) fails the "publishing a public package" condition outright, regardless of repository visibility, regardless of tooling version.**
   
   These two models are **mutually exclusive authentication mechanisms**, not complementary layers — a workflow uses one or the other, not `NPM_TOKEN` *and* `id-token: write` together for the same publish call. The original draft's combination of all of `NPM_TOKEN` + `id-token: write` + an explicit `--provenance` flag in one contract was internally incoherent, exactly as the first Spec Review pass identified.
3. **This repository's package manager is pinned `packageManager: "pnpm@9.6.0"` (root `package.json`, re-confirmed this pass) — not npm.** `changeset publish` detects the workspace's package manager and shells out to `pnpm publish`, not `npm publish`, when pnpm is in use (confirmed directly in `@changesets/cli`'s source: `publishTool.name === "pnpm" ? spawn("pnpm", ["publish", ...])`). **`pnpm publish --help` on pnpm 9.6.0 (this repository's installed version) lists no `--provenance` flag at all** (confirmed directly the first Spec Review pass: only `--tag`, `--access`, `--otp`, and a small set of other flags exist). pnpm's own OIDC/trusted-publishing support (confirmed via pnpm's public issue tracker and changelog, e.g. `pnpm/pnpm#9812`, `pnpm/pnpm#11513`, the pnpm 11.3 release notes) is a **pnpm-major-version-11-era feature, added roughly two major versions after this repository's pinned 9.6.0.**

**Three independent, compounding reasons provenance cannot be delivered, not one:**
1. `changeset publish` cannot forward `--provenance` regardless of which npm/pnpm version is present (finding 1) — a tool-level gap.
2. This repository's pinned `pnpm@9.6.0` supports neither the flag nor OIDC trusted publishing (finding 3) — a pinned-dependency-version gap.
3. **New this pass, and independent of both tooling gaps above: the project's own binding decision that `@ultimate/*` packages remain permanently restricted/private (C4 item 1) directly fails the "publishing a public package" condition both provenance models require** — this reason would still block provenance even if findings 1 and 2 were somehow resolved (a hypothetical future `@changesets/cli` version that forwards `--provenance`, and a hypothetical future pnpm upgrade with full OIDC support, would still not produce provenance for a package that stays `access: "restricted"`).

**Corrected decision:** given all three findings above, **no path to publish-time provenance exists for this repository's `@ultimate/*` packages as currently and permanently scoped (restricted/private), using this repository's currently-pinned tooling, or even using either provenance model's own newest supported form.** This is not solely a tooling-currency problem this repository could grow out of by upgrading dependencies — finding 3 is a standing, structural consequence of the project's own access-level decision, independent of any future pnpm or `@changesets/cli` version. **This Specification does not propose changing the access-level decision to unlock provenance** — that would invert the task's own instruction (the access decision is authoritative project intent, not a variable to solve for) and would contradict C4 item 1's binding status.

**Therefore: Track C's publish/authentication contract is token-based (`NPM_TOKEN`, Model A's authentication half only, without its provenance half), for restricted/private packages, as the only model this repository's project decision and currently-pinned tooling can coherently support together.** Provenance is recorded as a **known, structurally-foreclosed capability gap** (§7, §13 OQ-4), not a requirement this track's Implementation Plan can deliver under any near-term tooling change alone. This is not a silent scope reduction — it is the coherent contract both the project's own decision and the real tooling support, replacing an original contract that combined mechanisms which do not combine and that (this pass additionally found) contradicts the project's own access-level intent regardless.

**What this does NOT decide:** whether the project should ever revisit the restricted/private access decision itself, or whether a future custom, non-`changeset publish` release script could reach Model A's `--provenance --access public` flags for some future scenario where a subset of packages might go public. Neither is decided here — both are out of this Specification's scope, and the second directly contradicts the current, binding access decision unless that decision itself is revisited first (a future, separate decision, not this Specification's to make). Recorded as Open Question OQ-4, narrowed from the first pass's framing (see §13).

## 7. Provenance / Attestation (corrected; provenance is structurally foreclosed, not merely a tooling gap)

(Consolidates C5/R6 for direct traceability, per the task's required section structure. This section was substantively rewritten during Spec Review, twice — see C5 for the full evidence trail across both passes.)

- **What publish-time provenance would mean here, if achievable:** a cryptographically-signed attestation, generated at publish time, proving a given published package version was built by a specific, named CI workflow run from a specific commit — verifiable by any consumer via npm's own registry UI/API, without trusting Ultimate's own claim about how the package was built.
- **Two real, non-combinable mechanisms exist in the wider ecosystem** (confirmed via npm's own official documentation, fetched and re-verified with verbatim-quote extraction directly during this review): Model A (token-based, explicit `npm publish --provenance` flag, requires a public source repository, and requires the individual first-publish invocation to pass `--access public`) and Model B (OIDC Trusted Publishing, no token, automatic provenance, requires "publishing from a public repository" AND "publishing a public package" as explicitly separate, named conditions, per npm's own documentation quoted verbatim, requires npm CLI ≥ 11.5.1). Neither is a superset or subset of the other — a given publish call uses one or the other.
- **Neither mechanism is currently reachable through this repository's actual, pinned tooling — and, independently, neither is compatible with this repository's own binding access decision, regardless of tooling.** `changeset publish` (this repository's chosen publish mechanism, C1/C3) has no code path to forward a `--provenance` flag, in any version currently installed (`@changesets/cli@2.31.1`) — confirmed by direct source inspection, not assumed. Independently, this repository's pinned `packageManager: "pnpm@9.6.0"` predates pnpm's own OIDC/provenance support by roughly two major versions, and `pnpm publish --help` on the installed version lists no `--provenance` flag at all — confirmed directly on this machine. **Independently of both of those tooling gaps: `@ultimate/*` packages are decided (C4 item 1) to remain permanently restricted/private, and both provenance models require the published package itself to be public — a decision-level incompatibility, not a version-currency problem.** All three findings apply simultaneously; any one alone would already block provenance.
- **Corrected mechanism decision (C5, R5):** Track C's actual, deliverable publish contract is **token-based authentication (`NPM_TOKEN`), for restricted/private packages, without provenance** — the only model this repository's project decision and its currently-pinned tooling can coherently support together.
- **Distinguishing from Phase 0's Prime-source provenance:** see R6's own binding restatement above — two real, non-overlapping "provenance" concerns coexist in this repository by design (architecture discussion §7), not a naming collision to resolve. This correction does not change that distinction — it only changes whether the *publish-time* half is currently achievable, not whether the concept itself is well-defined.
- **Registry authentication vs. provenance, restated for this section (per C4's binding distinction):** a restricted/private package can authenticate and publish successfully via `NPM_TOKEN` (R5) while having zero provenance attestation (this section) — these are unrelated success/failure conditions. A successful, authenticated restricted-package publish is a complete, coherent Track C deliverable on its own; it does not need provenance to be "done."
- **What can be verified locally:** the *shape* of the release workflow YAML (does it reference `secrets.NPM_TOKEN` for authentication, does it correctly NOT claim `--provenance`/`id-token: write`/`--access public` given the findings above) — a static, file-content check, performable without any registry or remote.
- **What requires a real remote/registry:** whether a publish attempt actually succeeds, whether the `NPM_TOKEN` secret is valid, whether `access: "restricted"` behaves as expected for the `@ultimate` scope on the real registry. **None of these can be verified in this environment** — no git remote is configured (§4), matching exactly the same category of external-only check Track A's Task 11b already encountered and documented as environmentally blocked, not a Track C-specific new problem.
- **What is now a genuinely future, separately-scoped item, not part of this track's current deliverable, and requiring more than a tooling change alone:** achieving actual publish-time provenance would require *both* (a) a future pnpm major-version upgrade unlocking OIDC trusted publishing (or a future custom release script bypassing `changeset publish`/`pnpm publish` to reach Model A's flags directly) *and* (b) a separate future decision to revisit the restricted/private access commitment itself, since either provenance model's own "public package" condition cannot be satisfied while that commitment stands. Recorded as Open Question OQ-4 (§13, narrowed this pass) — deliberately not decided here, since resolving it is not required for Track C's core release-automation goal, and since revisiting the access decision is explicitly not this Specification's call to make.

- **OQ-4 (formerly OQ-5, narrowed this pass — two-part, both parts required together, neither alone sufficient):** given C5/R6's finding that publish-time provenance is foreclosed by three independent, compounding reasons (the `@changesets/cli` forwarding gap, the pinned `pnpm@9.6.0` version gap, and — new this pass — the restricted/private access decision itself), should the project ever pursue provenance in the future, and if so, does it accept that doing so requires **both**:
