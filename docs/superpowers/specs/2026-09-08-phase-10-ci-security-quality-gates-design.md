## 1. Scope and Motivation

### Why Track B first

The architecture discussion (§3) found five sub-tracks with different dependency shapes: A (testing/browser/visual/a11y) and E (SSR/hydration) both depend on tooling/scope decisions made in that same discussion but are large, two-tool (Storybook+Playwright) integration efforts; C (release engineering) depends on the migration-tooling-scope decision and is inherently smaller; D (operational documentation) has zero technical dependencies but is documentation-only. Track B (this document) was identified as having **zero architectural dependency on any other track**, is composed entirely of items the architecture discussion classified "Architectural decision required: No" (pure additive CI/tooling work), and directly extends CI patterns already proven three times in this repository (`provenance:validate`, `boundary:validate:{cli,mcp,ai}`, `ceiling:validate`). This makes it the lowest-risk, most immediately actionable Phase 10 work, consistent with the discussion's own sequencing recommendation.

This document was re-verified against current `main` before being written (not assumed from either prior document) — see §3.

### Scope

Track B covers exactly the ten items enumerated in the task brief, each traced to a specific Blueprint requirement in §2:

2. License scanning

## 4. Requirements

Each requirement below states exact behavior, inputs/outputs, failure behavior, gating semantics, determinism expectations, scope, and acceptance criteria. Numbered to match §1's ten scope items.

### R1 — Dependency vulnerability scanning

- **Behavior:** a CI step scans the resolved dependency tree (via the committed `pnpm-lock.yaml`) for known vulnerabilities and fails the build on findings at or above a defined severity threshold.
- **Inputs:** `pnpm-lock.yaml`, installed `node_modules` state.
- **Outputs:** machine-readable report (`--json`) plus a human-readable CI log summary; non-zero exit on qualifying findings.
- **Failure behavior:** CI job fails; the step must not silently continue on error (no `continue-on-error: true` without an explicit, separately-approved suppression mechanism — see R5 for how legitimate suppressions are handled).
- **Gating:** blocking — required status check on `main`.
- **Determinism:** vulnerability databases update independently of source changes, so this step is **not fully reproducible byte-for-byte across time** (a previously-passing commit can start failing if a new CVE is published against an already-pinned dependency) — this is expected and correct behavior for a vulnerability scan, not a defect; it must be documented as such wherever this gate is described so a future "why did CI start failing with no code change" investigation isn't treated as a regression in the gate itself.
- **Package scope:** whole-repository (root `pnpm-lock.yaml`, not per-package).
- **Tool selection (decided):** `pnpm audit`. **Evidence:** the repository already pins `packageManager: "pnpm@9.6.0"` (root `package.json`); `pnpm audit --help` was run directly against this session's installed `pnpm@9.6.0` and confirmed the command exists with exactly the flags this requirement needs — `--audit-level <low|moderate|high|critical>` (severity gating, built in), `--json` (machine-readable output), `-P`/`--prod` (scope to runtime dependencies), `--ignore-registry-errors` (documented by the tool itself as "useful when audit checks are used in CI... a build should fail because the registry has issues" — i.e., the tool's own docs distinguish a genuine finding from a registry outage, which this specification adopts: a registry-unreachable condition must NOT be treated as a passing scan, so `--ignore-registry-errors` is deliberately **not** used — see failure semantics below). No new dependency, no new account/service, zero ecosystem-compatibility risk, since it is invoked through the package manager already governing every other CI step in `.github/workflows/ci.yml`.
- **Severity threshold (decided):** fail on `high` or `critical` findings (`pnpm audit --audit-level high`). **Why:** `low`/`moderate` findings in transitive dependencies are common and frequently unfixable on a maintainer's timeline (no available patched version yet), which would make the gate too noisy to stay blocking in practice; `high`/`critical` is the threshold at which a finding represents a credible, actionable risk. This mirrors the same high/critical framing GitHub's own Dependabot alerts UI defaults to surfacing most prominently — cited as corroborating precedent, not as the basis of the decision, which rests on the noise/actionability tradeoff stated above.
- **Registry-unreachable behavior:** if the audit step cannot reach the registry, the step fails (not passes) — `--ignore-registry-errors` is explicitly not set, since silently passing on a registry outage would mean this gate can be defeated by an infrastructure failure, defeating its purpose as a security gate.
- **Acceptance criteria:** CI step exists; fails a synthetic test dependency with a known `high`+ vulnerability; passes on current `main`'s actual dependency tree (to be confirmed empirically at implementation time — this specification cannot run and commit a CI change to verify this, per its own scope boundary, but the pass/fail contract itself is fully determined here, leaving nothing for an implementation plan to invent).

### R2 — License scanning

- **Behavior:** a CI step enumerates the license of every resolved runtime and dev dependency and fails the build if any dependency's license is outside an approved allowlist.
- **Inputs:** `pnpm-lock.yaml` / installed `node_modules` package metadata (`license` field per `package.json`, where present).
- **Outputs:** a report listing every dependency and its detected license; non-zero exit on disallowed/unknown licenses.
- **Failure behavior:** fails the build. An "unknown license" (no `license` field, ambiguous SPDX expression, or a license string the tool cannot parse) must fail closed, not pass silently — consistent with Blueprint §2.3's MIT-only provenance discipline already established for Prime-derived source, extended here by analogy to the ordinary npm dependency graph (this is this document's own extension of an existing repository principle to a new context, not a direct Blueprint quote — recorded as such).
- **Gating:** blocking.
- **Determinism:** deterministic given a fixed lockfile — license metadata does not change without a dependency version change, unlike R1's vulnerability databases.
- **Package scope:** whole-repository.
- **Tool selection (decided):** `license-checker` (the `license-checker-rseidelsohn` maintained fork, or the original `license-checker` package — either satisfies this requirement identically since both expose the same `--onlyAllow`/`--excludePackages` CLI contract; exact package-name pick is a non-architectural implementation-plan detail, not left open as policy). **Evidence:** it runs entirely against locally-resolved `node_modules` metadata (no network call beyond what `pnpm install` already performed), has a built-in `--onlyAllow "<SPDX-list>"` flag that fails the process when any dependency's license isn't in the given list — this is exactly R2's allowlist contract, requiring no custom scripting to implement the pass/fail logic.
- **Excluding this repository's own workspace packages from the scan (corrected — the prior draft's wording was inaccurate):** the prior draft claimed this repository's 17 `packages/*` are `"private"`-unset-but-internal-in-practice and proposed `--excludePrivatePackages` to skip them. This is factually wrong: this session directly re-verified that **no `packages/*/package.json` declares a `"private"` field at all** (confirmed via `grep '"private"' packages/*/package.json` returning zero matches this session) — `--excludePrivatePackages` reads exactly that field, so it would exclude nothing here and is not the correct mechanism. The correct mechanism, using only behavior `license-checker` actually documents, is its **name-based exclusion flag** — `--excludePackages "@ultimate/ai@0.1.0;@ultimate/cli@0.1.0;..."` (one entry per in-scope workspace package, `name@version`) or the equivalent `--excludeScopes @ultimate` flag (excludes every package under the `@ultimate/*` npm scope by name pattern, not by any `private`/metadata field) — either correctly and verifiably excludes exactly this repository's own 17 workspace packages from being flagged against their own dependency-license policy, since each already declares `"license": "MIT"` in its own `package.json` (re-confirmed this session) and is not a third-party dependency this gate is meant to police. `--excludeScopes @ultimate` is the simpler, more maintenance-free choice (no per-package version string to keep in sync as versions change) and is the specific mechanism this specification selects.
- **Approved license allowlist (decided):** `MIT`, `Apache-2.0`, `BSD-2-Clause`, `BSD-3-Clause`, `ISC`, `0BSD`, `CC0-1.0`. **Why these seven:** each is OSI-approved, permissive (no copyleft/reciprocal obligation that could conflict with Ultimate's own MIT positioning per Blueprint §2.3), and each already appears somewhere in this monorepo's existing dependency tree in practice (MIT/ISC dominate the JS ecosystem broadly; Apache-2.0/BSD variants appear in common transitive dependencies of tools already in use, e.g. TypeScript-ecosystem and Node-ecosystem tooling) — this is a conservative, evidence-shaped starting allowlist, not an arbitrary list. Any dependency whose license falls outside these seven fails the gate and requires either an allowlist amendment (a deliberate, reviewed change to this list) or removal of the dependency — this is the intended, correct behavior of an allowlist-based gate, not a defect to work around.
- **Acceptance criteria:** CI step exists; fails a synthetic dependency with a disallowed/unknown license; passes on current `main`'s actual dependency tree (to be confirmed empirically at implementation time, same caveat as R1's acceptance criteria — the pass/fail contract and allowlist are fully determined here).

### R3 — SAST (Static Application Security Testing)

- **Behavior:** a CI step performs static analysis across the repository's own source (not third-party dependencies — that's R1/R2's job) for known insecure patterns (e.g., injection risks, unsafe eval, hardcoded-credential patterns).
- **Blueprint qualifier:** §29 says "SAST **where appropriate**" — the only conditional item in that list. This specification interprets "where appropriate" as: apply SAST to all TypeScript/JavaScript source under `packages/*/src/` and `scripts/`, since that is exactly the surface where an injection or unsafe-eval class of defect would matter; it does not extend to generated artifacts (`dist/`, `skills/*.md`, `packages/ai/dist/context/*.txt`) or to documentation/spec/plan markdown, since static-security analysis of prose or generated output is not a meaningful application of "appropriate."
- **Inputs:** repository source tree (scoped per above).
- **Outputs:** findings report (SARIF); non-zero exit / failed check on findings at or above the severity threshold defined below.
- **Failure behavior:** fails the build on a qualifying **new** finding, per the baseline/suppression contract defined immediately below (this replaces the prior draft's vague "initial baseline/suppression pass" wording with the exact contract required).
- **Tool selection (decided):** GitHub CodeQL (`github/codeql-action`), using its default JavaScript/TypeScript query pack (`security-extended` query suite, which includes the standard `security-and-quality` rules plus additional security-focused queries beyond the narrower default pack). **Evidence:** `.github/workflows/ci.yml` already targets `runs-on: ubuntu-latest` via GitHub Actions (`actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`) — CodeQL's action (`github/codeql-action/init` + `github/codeql-action/analyze`) is a first-party GitHub Actions integration requiring no new external account, no new secret, and no new billing relationship beyond what running GitHub Actions itself already implies, making it the lowest-friction SAST option for this specific CI platform. (Repository note: no `git remote` is currently configured for this local repository — confirmed this session — so CodeQL's GitHub Advanced Security code-scanning UI integration will only become visible once/if this repository is pushed to a real GitHub remote; the CI *step* itself runs and gates identically regardless, since CodeQL's SARIF output and exit-code behavior do not require the code-scanning UI to function as a CI gate. This is recorded as a known environmental fact, not a blocker to specifying the gate.)
- **Baseline/suppression contract and enforcement mechanism (decided, replacing the prior vague wording — this is the exact answer to "who consumes SARIF, how it compares against the baseline, and what causes CI failure"):**
  1. **CodeQL produces SARIF findings.** The `github/codeql-action/analyze` step runs CodeQL's `security-extended` query pack against the scoped source (`packages/*/src/`, `scripts/`) and writes its results as a SARIF file (CodeQL's own native output format — no custom format invented here).
  2. **A repository-owned validation script consumes that SARIF output.** CodeQL's own native GitHub-Advanced-Security code-scanning gate does **not** understand this repository's `SAST_BASELINE.md` grandfathering contract (no CodeQL feature is being relied on to implement custom, repository-specific baselining) — so a new script, `scripts/provenance/validate-sast-baseline.mjs` (named and placed to match this repository's existing `scripts/provenance/validate-*.mjs` convention — `validate-provenance.mjs`, `validate-cli-boundary.mjs`, `validate-mcp-boundary.mjs`, `validate-ai-boundary.mjs`, all confirmed present this session and all following the same "read some input, apply a repository-specific rule, exit non-zero on violation" shape), runs as a separate CI step immediately after `codeql-action/analyze` and reads that step's SARIF output file as its input.
  3. **The validator extracts a stable finding identity/fingerprint from the SARIF output.** CodeQL's SARIF output includes a `partialFingerprints` field per result — a version/line-number-independent identity CodeQL itself computes for each finding (a documented CodeQL capability, not invented by this specification). The validator reads this field as each finding's identity; it does not invent its own fingerprinting scheme and does not fall back to a brittle rule-ID+file+line exact match, since that would break under ordinary, unrelated line-number drift (e.g., adding code above a baselined finding).
  4. **The validator compares extracted fingerprints against `docs/architecture/SAST_BASELINE.md`.** `SAST_BASELINE.md` is a version-controlled, human-and-script-readable file (exact format — Markdown table vs. a structured list the script parses — is an implementation-plan-level detail per §16, not decided here since it doesn't change this contract) whose entries record each grandfathered finding's fingerprint plus rule ID + file + a one-line human note, established once at implementation time by running CodeQL against `main`'s then-current state and recording every finding it reports (this is the initial baseline — see point 6 for its one-way-door lifecycle).
  5. **Any finding not covered by the baseline causes the validation step to exit non-zero, and therefore fails CI.** The validator's own exit code is what CI gates on for this requirement — not CodeQL's native pass/fail, which has no baseline awareness. Concretely: for every SARIF result at `error`/`warning` severity (see severity threshold below), the validator checks whether that result's fingerprint appears in `SAST_BASELINE.md`; if any such result's fingerprint is absent from the baseline, the validator prints that finding and exits non-zero, failing the CI job.
  6. **Findings matching the baseline are grandfathered per the existing one-way-door contract:** a fingerprint may only enter `SAST_BASELINE.md` as part of the one-time initial-baseline population described in point 4 — no finding introduced after the gate first goes live may ever be added to `SAST_BASELINE.md`. The baseline file is frozen at gate-activation time except for deliberate removals (point 7). This is a deliberate one-way door: baselining exists only to unblock the gate's initial rollout against pre-existing findings, not as an ongoing escape hatch for new ones — the only legitimate way a new CodeQL finding stops failing CI is fixing the underlying code, never baselining it.
  7. **Removing a baseline entry is done through ordinary reviewed repository changes:** an entry is removed from `SAST_BASELINE.md` (e.g., because the underlying code was fixed) via an ordinary pull request / commit editing that file, reviewed by whoever reviews any other change to this repository — no special approval role is invented, consistent with this repository having no populated `CODEOWNERS` (confirmed pre-existing gap, GAP-012, not reopened here).
- **Severity threshold (decided):** the `validate-sast-baseline.mjs` validator only evaluates SARIF results at `error` and `warning` level against the baseline; `note`-level findings are read from the SARIF output but never compared against `SAST_BASELINE.md` and never fail the validator, regardless of baseline status, since they represent a code-quality observation rather than a security-relevant one under CodeQL's own severity taxonomy.
- **Determinism:** deterministic given fixed source and a fixed CodeQL/query-pack version; a query-pack version bump can change findings — same non-determinism class as R1's vulnerability database, and the same "this is expected, not a regression" documentation obligation applies.
- **Package scope:** whole-repository source, per the "where appropriate" scoping above (`packages/*/src/`, `scripts/`).
- **Acceptance criteria:** the CodeQL `analyze` step and the `validate-sast-baseline.mjs` step both exist and run in sequence; a synthetic insecure-pattern file placed in a scratch location produces a SARIF finding the validator does not find in `SAST_BASELINE.md`, causing the validator to exit non-zero and CI to fail; `SAST_BASELINE.md` is created from a real, empirically-run initial scan against `main`'s actual current source at implementation time (this specification does not assume `main` is clean — it specifies the exact mechanism for handling whatever the real first scan finds, which may be zero findings or may be several); the validator passes (exits zero) when every `error`/`warning` finding's fingerprint matches a `SAST_BASELINE.md` entry, and fails (exits non-zero) when at least one does not.

### R4 — Vulnerability monitoring / security-advisory process

- **Behavior:** this is a **process** requirement, not purely a CI-gate requirement — Blueprint §29 lists "vulnerability monitoring," "security advisories," and "patch releases" as security-process outputs. R1 (dependency scanning) provides the *detection* mechanism; this requirement covers what happens after detection: a documented process for triaging a finding, deciding whether it warrants an out-of-band patch release, and (where applicable) issuing a security advisory.
- **In scope for Track B:** the *mechanism* — i.e., R1's CI gate is the monitoring half of this requirement, satisfied by R1 directly.
- **Out of scope for Track B, belongs to Track D:** the *documented process itself* (who triages, how an advisory gets published, what "patch release" means procedurally) — this is exactly the content that belongs in a SECURITY.md-equivalent document, which architecture discussion §8 already assigned to Track D as Blueprint-traceable content. Track B's responsibility ends at "the scanning mechanism exists and produces actionable findings"; Track B does not author the triage/disclosure process document.
- **Acceptance criteria:** R1's CI gate satisfies the monitoring half; this requirement is otherwise a scope pointer to Track D, not an independent Track B deliverable.

### R5 — Malicious dependency/package review process

- **Behavior:** Blueprint §29 names "malicious package/dependency review" as a distinct line item from ordinary vulnerability scanning (a malicious package is not necessarily a CVE — it may be a supply-chain attack, typosquat, or post-install-script compromise that a CVE database has not yet catalogued).
- **In scope for Track B:** a CI-enforceable *mechanism*, to the extent one exists as an automatable check — specifically, `pnpm`'s own package-installation behavior already runs without arbitrary post-install scripts by default in recent pnpm versions unless explicitly allowed (this is a `pnpm` platform capability, not something this specification builds) — verifying this default has not been silently overridden (e.g., no `.npmrc`/`pnpm-workspace.yaml` setting re-enables broad `postinstall` script execution) is a concrete, checkable CI assertion.
- **Out of scope for Track B:** a full manual/human review *process* for evaluating new dependencies before they're added — that is an operational/contributor-workflow concern more naturally belonging to a CONTRIBUTING.md-class document (architecture discussion §8: CONTRIBUTING.md is optional, non-Blueprint-mandated) or to ordinary code-review discipline, not a CI gate. This specification does not invent a formal dependency-approval workflow beyond what R1/R2's automated gates already provide, since nothing in the Blueprint or the architecture discussion mandates one beyond "review" in the abstract.
- **Acceptance criteria:** a CI assertion confirming the repository's package-manager configuration has not re-enabled unrestricted install-time script execution; documented as this requirement's concrete, automatable satisfaction of §29's "malicious package/dependency review" line item, with the honest caveat that this is a narrow, mechanical check, not a comprehensive review process.

### R6 — Bundle-size CI enforcement and budget

- **Behavior:** extend `scripts/provenance/measure-package-size.mjs` to cover all publishable packages (not just `uix*`/`ng*`), wire it into CI, and establish a baseline for the currently-unmeasured packages.
- **Authoritative package count (decided, replacing the prior draft's contradictory "11 ... 10 ... corrected count" wording):** this specification defines "publishable package" identically to R8's definition (§ R8 below) — a `packages/*` directory that is not `"private": true` and has a `build` script producing `dist/`. Re-enumerated directly against `main` this session: **exactly 17 packages** satisfy this definition (`ai`, `cli`, `component-metadata`, `component-schema`, `mcp`, `ng-core`, `ng`, `react-core`, `react`, `themes`, `uix-data`, `uix-motion`, `uix-styled`, `uix-styles`, `uix-utils`, `vue-core`, `vue`). Of these, **7 already have a recorded baseline** in `docs/architecture/PERFORMANCE.md` (`uix-motion`, `uix-styled`, `uix-styles`, `uix-utils`, `uix-data`, `ng-core`, `ng`) and **10 have never been measured** (`react-core`, `react`, `vue-core`, `vue`, `themes`, `cli`, `mcp`, `ai`, `component-schema`, `component-metadata`). This 17/7/10 split is the single authoritative count for this document — no other count appears anywhere else in this specification.
- **Inputs:** each package's built `dist/` output (per its own `package.json` `main`/`module` entry resolution, matching the existing script's already-correct per-package entry-resolution logic).
- **Outputs:** extended `PERFORMANCE.md`-style table (or equivalent machine-readable output feeding a CI check) covering all 17 in-scope packages; CI pass/fail or informational report per the decided gating strategy below.
- **Gating strategy (decided): two-stage — Stage 1 informational, Stage 2 regression-gated.**
  - **Stage 1 (informational, first cycle):** the extended `measure-package-size.mjs` runs in CI on every push/PR, its output is recorded to `docs/architecture/PERFORMANCE.md` (Phase 10 section, extending the existing Phase 1/Phase 2 sections' format) and printed in the CI log, but the step does **not** fail the build. This stage exists specifically to produce one real, complete 17-package measurement — establishing the baseline Stage 2 needs — since no such complete baseline currently exists (`PERFORMANCE.md` covers only 7 of 17 packages today, per the count above) and `PERFORMANCE.md`'s own text explicitly disclaims its existing numbers as ever having been a budget.
  - **Stage 2 baseline lifecycle (decided — this is version-controlled repository state, not CI-run-local state):** the recorded per-package baseline (in `PERFORMANCE.md` or its Phase-10-era equivalent — exact file/format is implementation-plan-level, per R6's own acceptance criteria) is a **committed file in the repository**, updated only via an ordinary, reviewed commit/PR — never written or overwritten automatically as a side effect of a regular CI run. A regular push/PR's CI run reads the existing committed baseline; it does not write to it.
  - **Stage 2 comparison semantics (decided, corrected — this is the exact fix for the prior draft's self-approval gap):** for any PR, the gate compares that PR's measured `dist/` gzip size against the baseline **as it exists on the PR's merge-base with the base branch (`main`)** — i.e., the baseline committed to `main` *before* the PR's own changes, never a baseline value the PR itself introduces or modifies in the same diff. Concretely: CI checks out (or reads, via `git show <merge-base-sha>:docs/architecture/PERFORMANCE.md` or equivalent) the baseline file's content at the merge-base commit, not the PR branch's current HEAD version of that file, and compares the current measurement against *that* value. **This is true even when the PR itself edits the baseline file** — a PR that both changes a package's size and updates its own recorded baseline value in the same diff is still gated against the pre-PR (merge-base) baseline, not the PR's own updated number. A PR cannot make its own regression gate pass by simultaneously changing the code and the baseline it is measured against.
  - **Deliberately accepted size changes (decided):** when a size increase is intentional and reviewed (e.g., a legitimately larger new feature), the correct path is: the PR ships with its size increase, its CI run is gated against the pre-PR merge-base baseline as above (and may legitimately fail Stage 2 if the increase exceeds 15%, which is expected and correct — the gate is not bypassed), the PR is reviewed with the regression called out explicitly, and **a separate, explicit baseline-update change** (either a commit within the same PR that a human reviewer explicitly approves as "yes, update the baseline to reflect this accepted increase," or a follow-up PR) commits the new measured value as the new baseline going forward. The mechanism that makes this safe is that the *gate itself* never trusts a same-PR baseline edit — only a human reviewer approving the PR (with the size regression visible in the diff/CI output) can effectively "accept" it, and the baseline file update is what makes that acceptance durable for future PRs' comparisons, not what makes the current PR's own gate pass.
  - **Threshold (decided):** the step fails if a package's measured gzip size increases by **more than 15%** relative to the merge-base-committed baseline described above.
  - **Why 15%, and why relative-not-absolute (decided, with justification):** no absolute KB/MB number is set, because none of this repository's real measurements (§3's `PERFORMANCE.md` data) were ever validated as a "correct" target size — inventing one now would be exactly the unfounded assumption the task instructs against. A **relative regression** threshold requires no such absolute judgment; it only asserts that a package should not suddenly grow disproportionately relative to its own committed prior state, which is a defensible, evidence-free-of-magic-numbers policy. 15% is chosen as a deliberately loose first-cycle threshold (wide enough to avoid false-positive failures from ordinary, legitimate growth such as adding a new exported utility) rather than a tight regression-hunting threshold — it exists to catch gross accidental regressions (e.g., an accidentally-bundled dependency, a broken tree-shaking config), not to police routine size growth. This value may be tightened later once more measurement history exists; that future tightening is not decided here and does not need to be, since Stage 2's mechanism (merge-base-anchored comparison) is unaffected by the exact percentage chosen.
- **Determinism:** deterministic given identical source, dependency versions, and build-tool version (already noted correct in `PERFORMANCE.md`'s own text: "`ng-packagr`/`tsup` output is deterministic given identical source and dependency versions"). Stage 2's merge-base-anchored comparison is itself deterministic given a fixed, committed prior baseline value and a fixed merge-base commit — no non-determinism class comparable to R1/R3's vulnerability-database drift applies here.
- **Package scope:** all 17 packages per the authoritative count above.
- **Acceptance criteria:** `measure-package-size.mjs`'s package-discovery filter covers all 17 packages; Stage 1 runs and produces a complete first measurement for all 17 (10 packages gain their first-ever recorded baseline); Stage 2's regression comparison is implemented and verified to (a) correctly fail against a synthetic >15% size increase measured against a merge-base baseline, (b) correctly pass against a synthetic <15% increase, and (c) correctly **still fail** a synthetic case where the PR under test both increases a package's size by >15% and edits the baseline file in the same diff to a value that would make the increase look acceptable — proving the gate reads the merge-base version of the baseline, not the PR's own modified version.

### R7 — Coverage-threshold CI enforcement

- **Behavior:** add coverage collection to the Vitest configuration used across all in-scope `packages/*` test suites, and gate CI on a minimum coverage percentage once a real baseline exists.
- **Authoritative package scope (decided, replacing the prior draft's "to be reconfirmed at implementation time" deferral):** identical rule to R6/R8 — every `packages/*` directory that is not `"private": true` and has both a `build` script and a `test` script. Re-enumerated directly against `main` this session: **all 17 publishable packages** (the same 17 named in R6) each have a `test` script (confirmed via direct `grep` across every `packages/*/package.json` this session — all 17 return exactly one `"test":` match). This is the same 17-package set as R6/R8, not a separately-derived, smaller count — the prior draft's confusion between a `vitest.config.ts`-file-presence count (15) and the real test-script count (17) is resolved by using one consistent, deterministic rule (non-private + has `test` script) across every requirement in this document.
- **Coverage collection mechanism (decided):** `@vitest/coverage-v8` (Vitest's own first-party, V8-native coverage provider). **Evidence:** every `packages/*/vitest.config.ts` already uses `defineConfig` from `vitest/config` (confirmed this session across all 15 files matching that exact config-file name — the remaining in-scope packages configure Vitest inline via `package.json`/equivalent, not re-audited file-by-file in this pass but using the same `vitest` test runner per the workspace-wide `pnpm run test` command already in CI); `@vitest/coverage-v8` is Vitest's own documented, officially-maintained coverage provider requiring no separate instrumentation step (unlike Istanbul-based coverage, which requires source transformation) — the lowest-friction option for a project already fully committed to Vitest (ADR-022's "Vitest-everywhere consistency", cited in the Research doc and re-confirmed unchanged this session).
- **Aggregation / per-package semantics (decided):** coverage is measured and reported **per package** (matching this monorepo's existing per-package `test` script structure — there is no single root-level Vitest run today, only `pnpm -r --if-present run test` fanning out to 17 independent package-level Vitest invocations), with an aggregated repository-wide summary line in CI output for visibility. The **gating decision (Stage 2, below) applies per package**, not as a single repo-wide average — a per-package gate is more actionable (points directly at which package regressed) and avoids one large, well-tested package masking a regression in a small, poorly-tested one.
- **Exact coverage metric (decided):** **line coverage percentage**, per package. **Why line coverage specifically, not branch/function/statement:** line coverage is `@vitest/coverage-v8`'s simplest, most broadly understood metric and the one most directly comparable to the kind of number a Spec-Review threshold decision can reason about without additional tooling-specific interpretation (branch coverage in particular has well-known edge cases around short-circuit boolean logic that would need their own separate policy discussion, out of scope here). This does not preclude also *collecting* branch/function/statement data (the coverage provider reports all of them by default) — only line-coverage percentage is the number this gate acts on.
- **Baseline measurement procedure (decided): two-stage, same shape as R6.**
  - **Stage 1 (informational, first cycle):** coverage collection runs in CI across all 17 in-scope packages on every push/PR, the resulting per-package line-coverage percentages are recorded (e.g., appended to the same Phase-10 section of `PERFORMANCE.md`, or a dedicated `docs/architecture/COVERAGE.md` — exact file choice is an implementation-plan-level detail, not decided here since it doesn't change the gate's contract), but the step does **not** fail the build. This produces the real baseline this repository has never had (confirmed in §3: zero coverage number has ever been measured here).
  - **Stage 2 baseline lifecycle and comparison semantics (decided — identical model to R6's, applied to coverage):** the recorded per-package coverage baseline is **version-controlled repository state**, updated only via an ordinary, reviewed commit/PR, never auto-written by a regular CI run. For any PR, the gate compares that PR's measured line-coverage percentage against the baseline **as it exists on the PR's merge-base with `main`** — the pre-PR committed value, never a baseline the PR itself introduces or edits in the same diff. A PR that both drops coverage and edits the baseline file to mask the drop is still gated against the merge-base value; a PR cannot make its own regression gate pass by changing the baseline it is measured against in the same diff. A deliberately accepted coverage change (e.g., removing dead, untested code that legitimately lowers the denominator) follows the same accepted-change path as R6: the PR's own gate runs against the pre-PR baseline (and may legitimately fail, which is correct, not a bypass), reviewers see the drop explicitly, and a separate, explicitly-approved baseline-update commit (in the same PR with reviewer sign-off, or a follow-up PR) records the new value as the baseline for future comparisons.
  - **Threshold (decided):** each package's line-coverage percentage must not drop by more than **2 percentage points, an absolute delta,** relative to the merge-base-committed baseline described above (e.g., 80.0% → 77.5% is a 2.5-point drop and fails) — expressed as a flat percentage-point subtraction, not a relative-percentage-of-prior-value formula, since coverage is already expressed as a percentage and a percentage-of-a-percentage framing would be needlessly confusing. This gate's threshold is an absolute percentage-point delta, not a relative-regression percentage — the two must not be conflated (this document uses "relative regression" only for R6's byte-size comparison, and "percentage-point regression" for R7's own, differently-shaped comparison, consistently throughout). **Why 2 points, and why no invented absolute floor:** no absolute floor (e.g., "80% minimum") is invented, since no such number has ever been validated against this repository's actual, real test suites; a small, regression-catching delta is chosen instead of a large absolute bar, consistent with catching an accidental drop in testing discipline (e.g., a large untested code addition) rather than retroactively demanding a specific coverage philosophy this specification has no evidence to justify.
- **Determinism:** deterministic given fixed source/tests and a fixed coverage-tool version; Stage 2's merge-base-anchored comparison is deterministic given a fixed, committed prior baseline value and a fixed merge-base commit, same class as R6.
- **Acceptance criteria:** coverage collection runs across all 17 in-scope packages without breaking any existing test (all currently pass per the Phase 9 closeout verification); Stage 1 produces a complete first real baseline for all 17; Stage 2's regression comparison is implemented and verified to (a) correctly fail against a synthetic >2-point coverage drop measured against a merge-base baseline, (b) correctly pass against a synthetic <2-point drop, and (c) correctly still fail a synthetic case where the PR both drops coverage by >2 points and edits the baseline file in the same diff to mask it — proving the gate reads the merge-base version of the baseline, not the PR's own modified version.

### R8 — Generalized package pack/install integrity verification

- **Behavior:** generalize the Phase 9 `@ultimate/ai` packaging-test *mechanism* (pack → override → install → assert) to every publishable package in the workspace, accounting for each package's real (and, per §3's dependency map, sometimes deep and cross-cutting) `workspace:*` dependency graph.
- **What "publishable package" means in this repository (specification decision, made here with justification, not deferred):** a package under `packages/*` is in scope if it (a) does not declare `"private": true` and (b) has a `build` script that produces a `dist/` directory consumers actually import from. Cross-checked against §3: all 17 `packages/*` satisfy both conditions. `packages/uix` (the empty umbrella package, `.gitkeep`-only, never populated per the Phase 5-era gap registry, not re-verified in this pass since it is unrelated to Track B) is excluded — it has no `package.json` with a `build` script and is not a real package. This definition is a specification decision (not directly quoted from the Blueprint, which never uses the phrase "publishable package"), justified by: it matches exactly the set of packages that would break for a real consumer if their packaging were broken, which is the actual risk this requirement exists to catch.
- **How workspace dependencies affect standalone installation:** per §3's dependency map, a correct generalization must (1) compute each in-scope package's full transitive `workspace:*` closure (not just direct dependencies — e.g., `@ultimate/ng`'s closure includes `ng-core`, `uix-utils`, `uix-styled`, `uix-motion`, `uix-styles`, `uix-data`, `themes`, and transitively `themes`'s own closure of `react`, `vue`, and *their* closures — a materially larger graph than Phase 9's flat 2-package case), (2) pack every package in that closure via `pnpm pack`, in a topologically valid order (a package must be packed after its own dependencies are packed, since `pnpm.overrides` needs a real tarball path to point at — though because `pnpm.overrides` in the Phase 9 precedent points at tarball *paths*, not at each other, packing order across siblings that don't depend on each other does not matter, only true dependency order does), (3) wire every closure member into the scratch consumer's `pnpm.overrides` map pointing at each one's `file:` tarball path, matching the exact mechanism `packages/ai/test/packaging.test.ts` already proved works. The cross-cutting edges (`@ultimate/ng → themes → react/vue`) mean a generalized script cannot assume a package family is always a dependency leaf — it must be computed per-package from real `package.json` data, not hardcoded per the current `PACKAGE_PREFIXES`-style shortcut `measure-package-size.mjs` uses (that shortcut is acceptable for R6's simpler size-measurement case but is explicitly **not** an adequate pattern to reuse here, since R8 needs real dependency-graph awareness, not a directory-name-prefix filter).
- **What constitutes a successful integrity test:** for each in-scope package, after the pack→override→install sequence into an isolated scratch consumer directory (no `pnpm-workspace.yaml` membership, matching the Phase 9 precedent's isolation), the test must confirm: (a) `pnpm install` completes without error (proves the dependency graph resolves entirely from local tarballs, no registry reach needed for any `@ultimate/*` package), (b) the package's declared entry point(s) (`main`/`module`/`exports` map, and `bin` entries where present) resolve to real files that exist on disk under the installed `node_modules/@ultimate/<name>/` tree, (c) for packages whose `files` array includes generated artifacts (e.g., `@ultimate/ai`'s `dist/context/*.txt`), those specific artifacts are present — this per-package assertion detail is **not** hardcoded once in a shared script; each package's own test (or a shared script driven by per-package config) must derive its "what must exist" list from that package's own `package.json` `exports`/`files`/`bin` fields, not from a copy-pasted, package-specific list like Phase 9's original implementation used. This is the specific generalization gap this requirement closes — Phase 9's test proved the *mechanism*, not a *reusable, data-driven* implementation.
- **Special/private/internal dependency characteristics — do any packages need separate treatment?** Reviewed against §3's dependency map: no package in this workspace has a dependency characteristic (native addon, platform-specific binary, private-registry-only dependency) that would require different treatment from the pack/install/assert mechanism already proven. All 17 are pure TypeScript/JavaScript packages built by either `tsup` or `ng-packagr`. **No special-casing is required by current repository evidence** — this finding may need revisiting if a future package introduces a genuinely different packaging shape, but nothing in scope today does.
- **Inputs:** each in-scope package's built `dist/` output, its `package.json` metadata, its computed `workspace:*` transitive closure.
- **Outputs:** pass/fail per package; a scratch consumer directory (temp, cleaned up per-test, matching the Phase 9 precedent's `mkdtempSync`/`rmSync` pattern).
- **Failure behavior:** any package's integrity test failing fails the build; this is a correctness gate (a broken package published to a real registry would break real consumers), not a soft/informational check — no budget/threshold ambiguity applies here, unlike R6/R7.
- **Gating:** blocking.
- **Determinism:** deterministic given fixed source and fixed dependency versions; uses real `pnpm pack`/`pnpm install`, consistent with the Phase 9 precedent's already-proven, real (not mocked) approach.
- **Package scope:** all 17 packages defined as "publishable" above, run either as one shared parameterized test (data-driven, one case per package) or one test file per package — implementation-plan-level choice, not decided here, since both satisfy this specification's contract equally.
- **Cadence (decided):** **runs on every push/PR to `main`, scoped to only the packages actually affected by the change** — specifically, a package's integrity test runs if the diff touches that package's own `packages/<name>/` directory, or any package in its `workspace:*` dependency closure (per §3's dependency map), or any of this track's own new integrity-test tooling. **Evidence for this decision:** this session empirically timed the existing Phase 9 precedent (`pnpm --filter @ultimate/ai test -- packaging`, the closest real analog to what R8 generalizes) — the single-package pack step alone took ~0.27s, and the full 2-test suite (one `npm pack` listing check plus one real scratch-consumer `pnpm pack`→`pnpm.overrides`→`pnpm install` cycle across 3 real tarballs — `@ultimate/ai` plus its 2 direct `workspace:*` dependencies) took **6.89s** end-to-end (measured via `vitest`'s own reported test duration this session). Extrapolated against §3's real dependency-depth data — several packages (`@ultimate/ng`, `@ultimate/vue`) have transitive closures of 6-7 packages, roughly double `@ultimate/ai`'s 2-dependency case — a full, unscoped 17-package run is estimated in the low-single-digit-minutes range, not prohibitive but materially heavier than any existing CI step in `.github/workflows/ci.yml` (the entire current 20-step job completes in well under that on this repository's history). **Why path-scoped rather than every-push-unscoped or scheduled-only:** an unscoped every-push run pays this cost on every change even to unrelated packages (e.g., a `packages/uix-utils` change would still re-pack-and-install `@ultimate/mcp`, which shares no dependency edge with it) — wasted CI time with no corresponding correctness benefit, since a package whose own code and whose dependencies are both unchanged cannot have a newly-broken pack/install contract. A scheduled-only (e.g., nightly) cadence was rejected because it would let a genuinely broken package merge to `main` and stay broken for up to a full day before detection — unacceptable for a correctness gate (distinguished from R6/R7's threshold-based gates, where a delay before the gate becomes fully blocking is acceptable specifically because those are regression-detection concerns, not binary correctness). Path-scoping via the already-known `workspace:*` dependency graph (§3) gives the correctness guarantee of "affected packages always re-verified on every relevant change" without paying the cost for genuinely unrelated changes.
- **Acceptance criteria:** every one of the 17 in-scope packages passes a real pack→override→install→assert cycle when directly touched or when a dependency in its closure changes; the assertion content for each package is derived from that package's own manifest, not hardcoded per-package by hand; the path-scoping rule is verified to correctly select the right subset for at least one single-package change and one shared-dependency (e.g., `uix-utils`) change touching multiple downstream packages.

## 8. Performance/Coverage Gate Contract

R6 (bundle size: `@ultimate/*` packages measured via the extended `measure-package-size.mjs`, Stage 1 informational → Stage 2 blocking at >15% relative gzip-size regression per package) and R7 (coverage: `@vitest/coverage-v8`, line-coverage percentage, per-package, Stage 1 informational → Stage 2 blocking at >2-percentage-point absolute-delta regression per package) are both threshold-based gates. Neither invents an absolute number — `PERFORMANCE.md` states its own numbers were never meant as a budget, and no coverage number has ever been measured in this repository — so both use a **measure-first (Stage 1), then a regression gate compared against the version-controlled baseline as it exists at the PR's merge-base with `main` (Stage 2)** contract, fully specified in §4, not deferred. The merge-base anchoring is deliberate: it is what prevents a PR from updating its own baseline in the same diff to bypass its own gate (§4's R6/R7 sections spell out this exact non-bypass property).

## 10. Failure and Reporting Behavior

- Every blocking gate (R1–R3, R8) fails the CI job outright on a qualifying finding — no silent continuation, no auto-merge override without explicit human action (out of scope to specify branch-protection-rule mechanics here — that is a repository-settings concern, not a CI-workflow-file concern, and is not touched by this document).
- Every gate produces a human-readable summary in CI logs at minimum; machine-readable output (JSON/lcov/etc.) is preferred where the underlying tool supports it natively, to support future tooling (e.g., a dashboard) without committing to building one now.
- R1's inherent non-determinism (vulnerability databases change over time) must be documented directly in the CI step's own name/description (e.g., a comment or step summary noting "this gate can fail without a code change if a new CVE is published") so a future investigation isn't mistaken for a regression in the gate mechanism itself.

## 11. Testing/Verification Requirements

- R1–R2: each new CI step must be verified against both a known-bad synthetic case (proves the gate can actually fail) and current `main`'s real state (proves it doesn't false-positive on existing, already-shipped code) before being marked blocking.
- R3: the `validate-sast-baseline.mjs` validator must be verified against (a) a known-bad synthetic finding not present in `SAST_BASELINE.md` (proves it fails CI), (b) a synthetic finding that does match a baseline entry (proves it does not false-positive on grandfathered findings), and (c) current `main`'s real state via a genuine initial CodeQL run (establishing the real `SAST_BASELINE.md` content, not an assumed-empty baseline).
- R6: the extended `measure-package-size.mjs` must be run against a fresh `pnpm run build` of all 17 packages and produce a complete table before any gating logic is added, matching the existing script's own established one-shot-measurement-first pattern from Phases 1–2. The merge-base-anchored comparison (§4) must additionally be verified against the specific non-bypass case: a synthetic PR that both increases a package's size beyond the threshold and edits the baseline file in the same diff must still fail.
- R7: coverage collection must be added and run once, informationally (Stage 1), before Stage 2's regression gate activates — the resulting real per-package percentages become each package's first recorded baseline, per R7's already-decided two-stage contract, not an assumption. The same merge-base non-bypass case from R6 must be verified for R7's coverage gate.
- R8: the generalized integrity test suite must be run against all 17 packages and pass before being marked blocking; must also be verified to correctly *fail* against at least one deliberately broken synthetic package (e.g., a scratch package with a `files` array omitting a file its `exports` map references) to prove the test isn't vacuously passing.
- All of the above follow this repository's established pattern (seen throughout Phases 6–9): a new validation mechanism must be proven to both pass on real good state and fail on real bad state before being trusted as a gate — never accepted on "it ran without erroring" alone.
