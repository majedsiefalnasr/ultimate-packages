## 2. Decision and alternatives

**Retain the current ESLint, Prettier, TypeScript and package-test commands.** They already define the repository-wide policy and are invoked directly by CI. Replacing them with a different linter/formatter would add a migration and a second interpretation of the existing debt without evidence that the tools themselves are defective. Repair GAP-092 to a zero-finding lint result and a passing full `format:check`; do not adopt an indefinite grandfathered baseline, broadly ignore failing paths, disable substantive rules, or lower CI severity merely to turn the job green. The existing narrowly documented Prime-derived rule exception remains subject to its provenance rationale.

**Use Husky to install versioned local hooks and lint-staged to select staged files for `pre-commit`.** Native `.git/hooks` files are untracked and per-clone; a committed `core.hooksPath` target would still need a per-clone setup step. Husky provides a documented `prepare` installation path for a private pnpm workspace and committed hook scripts. lint-staged filters staged files and handles partially staged files; it is selected for that boundary rather than hand-written filename parsing. Its default backup/hide/restore behavior is a reason to require explicit preservation tests before adoption, not permission to discard or auto-stage unrelated changes. [Husky setup](https://typicode.github.io/husky/get-started.html), [Git hook semantics](https://git-scm.com/docs/githooks), and [lint-staged behavior](https://github.com/lint-staged/lint-staged#readme) are supporting tool references; the repository-specific contract is below.

| Alternative                                                   | Disposition                                                                                                                                                       |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No local hooks; rely solely on CI                             | Rejected for this scope: failures surface only after a push/PR, while the user has requested local commit and push feedback. CI remains authoritative.            |
| Hand-written tracked hooks plus manual `core.hooksPath` setup | Rejected: the manual per-clone step is easy to miss and does not provide staged-file/partial-staging handling without new custom code.                            |
| Husky plus lint-staged                                        | Selected for versioned hook activation and staged-file selection. Only the hook tools are added; the existing quality engines and root CI commands stay in place. |

No new ADR is required: GAP-092 explicitly says no architectural decision is needed, and this local-tooling choice does not change the Blueprint or protected decisions. The Implementation Plan must verify current tool versions and choose compatible, lockfile-pinned releases; this Spec does not assert that an uninstalled version has already been tested in this repository.

## 3. Required target behavior

### R1 — Repair and preserve the quality policy

1. Inventory every current ESLint finding by path, rule, and cause at the implementation baseline. Correct owned-code defects and obsolete/inapplicable inline directives. Remove directives naming unconfigured React plugin rules: those directives have no active policy role in the current ESLint configuration. Do not add React plugins or enable new rules merely to make those directives parse, and do not mask other errors by a blanket rule disable. Fixes that can change runtime behavior require relevant package tests and semantic review; an actual component behavior correction follows its own scope and authorization under ADR-052 rather than being hidden in a lint cleanup.
2. Inventory all Prettier failures by path and provenance class. Bring every file in the existing formatter scope into compliance. Prefer mechanical, reviewable formatting batches, but do not blindly rewrite Prime-derived or provenance-sensitive source: preserve required notices and attribution, inspect any semantic or generated-output change, and reconcile file-level provenance records if a previously verbatim file is intentionally modified. Any proposed new ignore must be justified by a file's non-owned/generated/invalid-fixture role, not by the count of failures. The existing formatter scope must not silently shrink.
3. Preserve `pnpm run lint`, `pnpm run format:check`, and the existing typecheck/test scripts as the canonical whole-repository checks. Make the root `lint` command fail on any ESLint warning as well as any error, using `--max-warnings=0` or an equivalent verified configuration while retaining its name and whole-repository scope. Changes to configuration are allowed only to correct demonstrably wrong or obsolete configuration, with before/after rule and file-coverage evidence. Do not replace a failing command with a narrower command under the same name or turn errors into warnings to pass CI.

### R2 — Fast, index-aware `pre-commit`

1. A fresh development install activates a committed `pre-commit` hook through Husky. The hook first rejects staged whitespace errors (`git diff --cached --check` or equivalent), then runs lint-staged on added/copied/modified/renamed staged files. It invokes the existing ESLint policy for staged JS/TS-family files that ESLint currently handles, with `--max-warnings=0` or an equivalent verified warning threshold, and Prettier **check** (not write) for staged formatter-supported files, including Vue and documentation where applicable. Existing ignore rules remain in force; no new file-type promise may exceed what the installed tools actually parse.
2. The hook is read-only with respect to source and index content: it must not run `eslint --fix`, `prettier --write`, `git add`, or an equivalent automatic re-staging action. lint-staged's temporary state handling must restore the original index and all unstaged/untracked work on both pass and failure, including partially staged files. If that cannot be demonstrated safely with the selected tool version, Plan Review must choose a safer staged-content mechanism before implementation. A commit with no relevant staged files succeeds without running whole-repository quality commands.
3. A staged ESLint warning or error, or a staged format violation, exits nonzero and prevents the local commit. The hook does not run whole-workspace typecheck or tests on every commit; those belong to `pre-push` and CI. Local hooks can be bypassed by Git/user configuration and therefore are feedback, not the authoritative CI gate.

### R3 — Broader `pre-push`

1. A committed Husky `pre-push` hook runs the existing whole-workspace `pnpm run build`, `pnpm run typecheck`, and `pnpm run test`, in that order, with a nonzero exit on any failure. The build supplies the package artifacts required by the existing test suites, matching CI's prerequisite order. These checks are intentionally broader and less frequent than staged-file checks, but omit the browser, security, coverage, and release jobs that belong in CI. Do not introduce an affected-package selector, skip React, or alter the tests to hide GAP-089. A nonzero hook result prevents a normal local push; CI continues to run its own commands for all PRs and `main` pushes.
2. GAP-089 currently makes the root test command fail on `main`. This is a known **activation dependency** for a successful normal `pre-push`, not authorization to fix GAP-089 inside this scope. The Implementation Plan must either sequence final hook activation after GAP-089 is independently repaired, or return to Plan Review with evidence for an equally complete, explicitly approved test contract. Until then, a passing `pre-push`/whole-test result must not be claimed. No permanent skip, allow-failure wrapper, or default bypass is acceptable under this Spec.
3. Hook installation and invocation must work from a fresh clone with the repository's pinned pnpm and supported Node setup. A CI install must not rely on, or be blocked by, local hook execution. Document the ordinary manual commands and Git's bypass limitations without presenting hooks as a substitute for CI.

### R4 — CI and regression visibility

1. Keep `.github/workflows/ci.yml`'s direct full `lint`, `format:check`, `typecheck`, and `test` steps, their push/PR triggers, and existing failure propagation. Do not add a CI exception, `continue-on-error`, changed-path exclusion, or baseline bypass for GAP-092. New hook scripts must not become a prerequisite for CI's quality commands.
2. Once GAP-092 debt is repaired, the full lint and format commands must exit zero on the implementation commit; separate synthetic warning-level and error-level ESLint violations must each make the whole-repository lint command exit nonzero, and a new synthetic formatting violation must make the full format command exit nonzero. Existing violations may not disappear solely through a newly broad ignore or suppression. CI must show the same checks executing against the reviewed SHA. A passing GAP-092 pair does **not** imply the unrelated root test or whole workflow is green.
3. Preserve Track B's other CI security, provenance, coverage, package-boundary and integrity gates. Preserve Blueprint testing and upstream-source obligations. This specification does not close GAP-089/091/093/094 or alter GitHub branch-protection settings.

## 5. Boundaries and next gate

Expected implementation surfaces are root `package.json`/lockfile for the two hook tools and install wiring, committed hook/config files, focused lint/config fixes, formatting fixes, and any provenance record that an actual source edit makes necessary. `.github/workflows/ci.yml` should need no behavior change because the full checks are already wired. The Implementation Plan must enumerate exact files and batch the broad formatting diff for review; this Spec does not authorize those edits.

The locally available `COMPLETION_REGISTER.md` must remain untouched at this stage. At eventual, separately authorized closeout, reconcile its C01/GAP-092 coverage against merged evidence and the gap registry; do not silently mark GAP-092 resolved from a Spec, hook installation, or local run alone.

**Next gate: Spec Review.** After approval, prepare a single bounded Implementation Plan and submit it to Plan Review. Implementation, installation, commit, push, PR, and tracking updates each remain outside this gate.
