## 2. What the Blueprint already decides (not open questions)

Restated, not re-derived — Phase 8 does not get to relitigate these:

- **ADR-010 (Accepted):** MCP must remain optional and must never be a runtime dependency. Reserved as scaffolding only since Phase 0 (`packages/mcp`).
- **Blueprint §5 (MCP package boundary):** MCP's responsibilities are "expose Ultimate knowledge and tooling through MCP; component discovery; API lookup; documentation retrieval; examples; project-aware guidance; migration assistance; framework-aware queries." - **Blueprint §40 (Definition of Done):** "AI/MCP quality where those phases are enabled" is a named, non-optional axis of platform production-readiness (conditional on the phase being enabled — MCP is explicitly optional per ADR-010).

This is a concrete, load-bearing fact for Phase 8: the compatibility manifest already has a reserved slot for an MCP version axis, but populating it is explicitly out of `matchCompatibility()`'s current scope — extending the resolver to read it would be a CLI-side change, not something Phase 8 does unilaterally.

This is a directly reusable enforcement pattern (not a decision Phase 8 needs to re-litigate) for an equivalent `boundary:validate:mcp` gate.

This is a real, load-bearing shift in scope for Phase 8: the "read structured Ultimate metadata rather than depend on arbitrary source parsing at runtime" instruction in §23 is no longer speculative — the exact `ALL_COMPONENTS` array MCP must read already exists, is built, is typed, and is already being consumed the same way by a sibling package (CLI) using the same import (`import { ALL_COMPONENTS } from "@ultimate/component-metadata"`).

It remains true that Phase 9 (AI Skills/LLM context) has no committed spec — `packages/ai` and repo-root `skills/` are still `.gitkeep`-only. Any MCP behavior that would require a Skills package or generated LLM-context artifacts (`llms.txt`, etc.) to exist is out of reach and stays deferred.

## 4. What "read structured metadata, not runtime source parsing" concretely means here

§23's constraint is the load-bearing rule for this phase's entire I/O surface, so it is worth making concrete against the real, closed artifacts rather than restating it abstractly.

Confirmed by reading the real metadata package and its consumer (`packages/cli/src/commands/doctor.ts`, `generate.ts`):

- The **only** structured metadata source that exists today is `@ultimate/component-metadata`'s `ALL_COMPONENTS: ComponentMetadata[]` — a flat, in-memory, statically-imported array (not a database, not a file MCP would need to parse itself, not an API). Reading it is a plain ESM import, already proven twice (CLI's `doctor.ts`/`generate.ts`).
- There is **no separate "documentation" or "examples" artifact** anywhere in the repository distinct from this metadata. `ComponentMetadata.guidance` (`usageNotes`, `antiPatterns`, `migrationNotes`) is optional and, per direct grep confirmed below (§7), populated on **zero** of the 8 real records today. Any Phase 8 claim of exposing "documentation retrieval" or "usage examples" (§23's potential-capabilities list) beyond what `ComponentMetadata.api.*.props[].description` and the record's own `description` field already carry would be fabricating content beyond the real, closed proof set — exactly what GAP-027's closure and Phase 6/7's own precedent explicitly disciplined against.
- "Arbitrary source parsing at runtime" concretely means: MCP must never read `.ts`/`.tsx`/`.vue` component source files, parse ASTs, or introspect `packages/{ng,react,vue}` at request time to answer a query. The `ComponentApi.props[]`/`events[]` facts already baked into `ALL_COMPONENTS` at Phase 6 authoring time are the only source of prop/event truth MCP may surface — never a live re-derivation.
- A concrete boundary test, mirroring Phase 7's research (§4 of the CLI research doc): if a proposed MCP tool would require reading anything outside `@ultimate/component-metadata`'s exported `ALL_COMPONENTS` (or, where genuinely justified, the same compatibility-manifest/CLI-adjacent facts CLI already reads) — refuse it in v1. If it only requires reading/filtering/formatting facts already present in `ALL_COMPONENTS`, it is in-bounds.

## 5. MCP server/transport model — external-source research, clearly separated from repository evidence

The Blueprint does not specify a transport, SDK, or server-shape for `@ultimate/mcp` anywhere in the text (§23 lists only *capabilities*, never *mechanism*). This is a case where external facts about the Model Context Protocol itself are necessary to ground what "a separate package exposing capabilities through MCP" concretely requires, and must be clearly separated from repository/Blueprint evidence per this task's own instructions.

**External-source evidence** (general MCP protocol knowledge, not sourced from this repository):

- MCP defines three request-served primitive types a server can expose: **tools** (invokable, side-effect-capable actions with a JSON-schema input and a structured output — the natural fit for a "search"/"lookup" query), **resources** (addressable, readable data the host can fetch by URI — the natural fit for exposing a stable, whole-record document), and **prompts** (reusable prompt templates a host can surface to a user). A server is not required to expose all three.
- MCP servers run over one of two standard transports: **stdio** (the server is spawned as a local subprocess, communicates over stdin/stdout — the default for CLI-invoked, locally-installed servers) or **HTTP-based transports** (for remote/hosted servers). A locally-installed npm package invoked by an AI coding tool (the common integration pattern for "an MCP server shipped as part of a developer-tooling npm package") uses stdio.
- The reference TypeScript SDK for building an MCP server (`@modelcontextprotocol/sdk`) is the de facto standard implementation surface for a Node/TypeScript MCP server; it is what most first-party and community MCP servers (including, per `AI_ARCHITECTURE.md`'s own note, PrimeVue's shipped `mcp` package) are built on.

**Repository/Blueprint evidence bearing on this choice:**

- `AI_ARCHITECTURE.md` (Phase 0 artifact) explicitly flags: *"PrimeVue 4.5.5 already ships its own `mcp` and `metadata` sibling packages — useful prior art to review during Phase 6/8 planning. No action taken in Phase 0."* This is a direct, named instruction from the repository's own prior-phase documentation to consult PrimeVue's real, shipped MCP package as prior art now that Phase 8 planning has arrived. **This research does not have live access to PrimeVue's actual `@primevue/mcp` package source** (no such package is vendored, pinned, or present anywhere in this repository's `node_modules` or provenance records) — it is named as a documentation pointer, not a dependency Phase 8 incorporates or is required to structurally mirror. Reviewing its real source (if desired) would need to happen via an external npm/GitHub lookup outside this research pass's repository-bound scope; this research flags the gap rather than fabricating what that package contains.
- ADR-010 and Blueprint §5/§6 both frame MCP as strictly optional and never a runtime dependency of the framework packages — this is consistent with (and reinforces the correctness of) a stdio-transport, locally-installed, opt-in server model: nothing about a stdio MCP server invoked by a developer's AI tool creates a runtime dependency for `packages/{ng,react,vue}`.
- The repository's own build/package conventions (uniform across every real package: `type: module`, ESM-only `tsup` build, `dist/index.mjs` + `.d.mts`, `bin` entry point pattern already used by `@ultimate/cli` for its own `ultimate` executable) directly template how `@ultimate/mcp` would be packaged and invoked, independent of any MCP-specific research.

**Architectural inference (this research's own synthesis, flagged as inference, not asserted as Blueprint fact):**

- Given (a) no Blueprint text mandates a specific transport, (b) the repository's own CLI package already established a `bin`-entry-point-invoked, locally-installed Node package pattern, and (c) MCP's own ecosystem convention for exactly this kind of "an AI coding tool spawns a local server to query structured project/library knowledge" use case is stdio, a stdio-transport, locally-spawned server invoked via a `bin` entry point (mirroring `@ultimate/cli`'s own `bin: { ultimate: "./dist/bin.mjs" }` shape) is the natural, low-risk mechanism choice. This is an inference this research recommends the specification adopt, not a Blueprint-mandated requirement — flagged explicitly as **NEEDS ARCHITECTURAL DECISION** is not warranted here because no repository evidence contradicts it and no second real option has comparable support; see §7 Fork 1 below for the full fork treatment.

## 6. Component discovery/lookup semantics — grounded against the real 8-record proof set

Blueprint §23's "potential capabilities" list (component search, API lookup, usage examples, accessibility guidance, theme/token lookup, migration assistance, framework-aware recommendations, project-aware information, CLI/tooling discovery) is explicitly qualified "potential" — not a required minimum set. Cross-checked against what `ALL_COMPONENTS`'s real 8 records actually populate, confirmed by direct read of every record file (`button.ts`, `checkbox.ts`, `dialog.ts`, `menu.ts`, `paginator.ts`, `scroller.ts`, `table.ts`, `tooltip.ts`) and the `package-exports.test.ts`/individual test files' assertions:

| §23 candidate capability | Backed by real data today? | Evidence |
|---|---|---|
| Component search | Yes — `name`, `category`, `description` populated on all 8 | `ComponentIdentity` required fields |
| API lookup (props/events) | Yes — `api.{ng,react,vue}.props[]` populated on all 8; `events[]` empty on all 8 (verified: no component in the proof set has custom events per each record's own header comment, e.g. Button's) | `component-metadata.ts`, `api.ts` |
| Usage examples | **No** — no `examples` field exists anywhere in `ComponentMetadata`'s schema (`component-metadata.ts`'s type intersection has exactly 6 optional facets: `api`, `accessibility`, `style`, `relationships`, `provenanceRef`, `guidance` — no `examples`) | Direct schema read |
| Accessibility guidance | Partial — `accessibility.{verifiedRoles,verifiedAriaAttributes,guidance}` exists as a schema facet but is optional; not verified populated on all 8 records in this pass (would need a per-record grep to confirm exact coverage — flagged `UNVERIFIED` below) | `accessibility.ts` |
| Theme/token lookup | **No** — `style.{componentName,styleModuleRef}` identifies which style module a component maps to, but carries no actual token values, CSS custom-property names, or theme-preset data; that lives in `@ultimate/themes`, a package `ComponentMetadata` does not reference structurally beyond the style-module-name string | `style.ts` |
| Migration assistance | Partial — `guidance.migrationNotes` exists as an optional string field; not verified populated on any real record in this pass | `guidance.ts` |
| Framework-aware recommendations | Yes — every fact in `ComponentMetadata` is already keyed per-framework (`packages.{ng,react,vue}`, `api.{ng,react,vue}`) — a query scoped to one framework is a direct filter, not new data | Schema-wide |
| Project-aware information | Partial — `@ultimate/cli`'s `detectFramework()`/`compatibility-manifest.json` already implement "detect what framework/version a target project uses" (Phase 7); MCP could reuse the same detection logic, but this would be a **new dependency edge from MCP onto CLI's internals** — not yet decided (see Fork 2, §7) | `detect-framework.ts`, `compatibility.ts` |
| CLI/tooling discovery | **No concrete data exists for this today** — no registry of "what CLI commands exist and what they do" beyond `cli.ts`'s own hardcoded `KNOWN_COMMANDS` array, which is CLI-internal, not exported as metadata | `cli.ts` |

This table is the single most important piece of evidence this research produces: **it establishes exactly which of §23's "potential capabilities" have real backing data today, and which would require either fabricating example/theme-token/CLI-discovery data that doesn't exist (out of scope, would violate GAP-027/Phase-6-precedent's "no fabrication beyond real records" discipline) or extending `@ultimate/component-metadata`'s own schema (which this task's scope constraints explicitly forbid — "Do not expand the component metadata proof set merely for MCP").**

## 7. Candidate architectural forks considered, and their resolution

### Fork 1 — Transport/server model: stdio-only vs. also supporting HTTP

- **Options:** (a) stdio-only, locally-spawned via a `bin` entry point, matching `@ultimate/cli`'s own established shape; (b) stdio + an HTTP transport option for a remote/hosted deployment.
- **Repository/Blueprint evidence:** No Blueprint text anywhere specifies a transport. ADR-010/§5/§6 establish MCP as strictly optional, locally-invoked tooling — nothing in the Blueprint frames MCP as a hosted service. The repository has zero hosting/deployment infrastructure of any kind (confirmed: no `apps/*` beyond empty scaffolding, no server-deployment config anywhere).
- **External-source evidence:** stdio is the standard, lowest-friction transport for exactly this "AI coding tool spawns a local server for a locally-installed npm package" use case; HTTP transports are used for remote-hosted MCP servers, a materially different deployment model.
- **Tradeoff:** stdio-only is simpler, matches the CLI precedent, and requires zero new infrastructure decisions (packaging, hosting, auth). Adding HTTP support now would be building infrastructure (a server deployment story) with no named consumer or Blueprint requirement for it — direct YAGNI territory, and this task's scope constraints explicitly forbid inventing infrastructure the Blueprint doesn't ask for.
- **Recommendation:** (a) stdio-only for v1. This is a specification-level default, not a Blueprint-mandated requirement, but no repository evidence favors (b) and no named consumer needs it. Not escalated as **NEEDS ARCHITECTURAL DECISION** — the evidence asymmetry is strong enough (zero hosting infra exists, zero Blueprint text calls for it) that this is an ordinary scoping default, the same kind Phase 7's research made for its own command-subset scoping (research doc §7, fork 3).

### Fork 2 — Does MCP depend on `@ultimate/cli` for project-detection logic, or does it duplicate/independently implement it?

- **Question:** `@ultimate/cli`'s `detectFramework()` (framework detection from a target project's `package.json`/`angular.json`) and `matchCompatibility()` (compatibility-manifest resolution) are exactly the kind of "project-aware information" §23 lists as a potential MCP capability. Should `@ultimate/mcp` depend on `@ultimate/cli` as a library to reuse this logic, or should it not depend on CLI at all?
- **Repository/Blueprint evidence:** Blueprint §6's prohibited-direction diagram is explicit: `Ultimate Components → CLI → MCP → AI` is forbidden — and critically, **this diagram places CLI upstream of MCP in the prohibited chain**, meaning the Blueprint's own stated bad pattern is precisely "MCP depends on CLI, which depends on Components." Reading this literally: the diagram is naming a prohibited *chain of dependency*, not asserting that CLI→MCP is a *desired* direction that's merely being called out as also-prohibited when reversed. The permitted direction diagram (`Component Source + Component Metadata + Documentation → CLI / MCP / AI / Skills / LLM outputs`) draws CLI and MCP as **parallel, independent siblings** both fed by the same upstream (metadata/docs/source) — not one feeding the other in either direction.
- **Tradeoff:** If MCP depends on `@ultimate/cli` (e.g., importing `detectFramework`/`matchCompatibility` as a library), that is a real new package dependency edge that: (a) is not named or required by §23 (which only requires reading *metadata*, not CLI internals), (b) risks exactly the chain pattern §6's diagram names as prohibited, and (c) was never anticipated by Phase 7's own boundary-enforcement CI gate (`validate-cli-boundary.mjs`), which currently proves `@ultimate/cli` has no dependency on `{ng,react,vue,themes}` but says nothing about `@ultimate/mcp` depending on `@ultimate/cli` — meaning this edge is not yet CI-guarded either way and needs an explicit decision, not silent adoption. If MCP does not depend on CLI, "project-aware information" is either dropped from v1 scope or MCP independently re-implements a minimal, narrow version of framework-detection logic (a real, if small, duplication).
- **Recommendation:** MCP must not depend on `@ultimate/cli`. This is directly supported by the sibling-not-pipeline reading of §6's/§18's/§22's three separate diagrams (all three draw MCP as a parallel consumer of metadata, never as downstream of CLI), and is the safer reading of the prohibited-direction diagram's literal ordering. Project-aware "is this framework/version compatible" information, if included in v1 at all, should be scoped to reading the same underlying data sources CLI itself reads (`compatibility-manifest.json`, `@ultimate/component-metadata`) directly and independently — not by importing CLI's code. Given this task's explicit constraint to not silently broaden `@ultimate/cli` and not invent new cross-package coupling, and given the "project-aware queries" objective is one of four named Phase 8 objectives in §35 (so cannot simply be dropped without a documented deferral), the specification should scope "project-aware" narrowly (e.g., accepting a caller-supplied framework name/version rather than doing its own filesystem project detection) rather than duplicating `detectFramework()`'s filesystem-walking implementation. **This narrow-scoping approach is a specification-level design choice this research recommends, not a remaining fork requiring escalation** — no Blueprint text is contradicted by either the "accept caller input" or "duplicate minimal detection" sub-options, so the specification has latitude to pick the smaller-surface one.

### Fork 3 — Tool/resource/prompt boundary: which MCP primitive(s) does v1 use?

- **Question:** Given MCP's three primitive types (tools, resources, prompts — external-source fact, §5), which does `@ultimate/mcp` v1 expose?
- **Repository/Blueprint evidence:** §23's capability list ("component search," "API lookup," "usage examples," etc.) is phrased entirely as *query-shaped* actions — a caller supplies a search term or component name and gets back a filtered/formatted answer. This maps naturally onto MCP **tools** (invokable actions with structured input/output), not resources (static, URI-addressable documents) or prompts (reusable prompt templates for a human user to select). No Blueprint text anywhere mentions prompt templates or a resource-browsing model.
- **Tradeoff:** Tools-only is the minimal primitive surface consistent with every named capability being action/query-shaped. Adding resources (e.g., exposing each of the 8 components as a browsable `ultimate://component/button` URI) would be a plausible *future* enhancement but has no named Blueprint requirement and no current consumer need — it would be speculative feature surface the task's scope constraints (§5 "Do not turn MCP into a build/compiler/bundler/dev-server layer," and the general "do not design speculative features merely because MCP supports them generally" instruction) directly caution against. Prompts are not mentioned anywhere and have no evident use case against 8 flat metadata records.
- **Recommendation:** Tools-only for v1. Justified directly by every §23 capability being query-shaped and no Blueprint text or repository evidence calling for resources/prompts. Not escalated — this is the same "don't build speculative surface the Blueprint doesn't ask for" discipline already applied by Phase 6 (schema-only fields with no example gallery) and Phase 7 (five commands, not nine).

### Fork 4 — Which of §23's "potential capabilities" does v1 actually implement, given §6's table shows uneven data backing?

- **Question:** Given §6's table above shows only 3 of 9 listed capabilities are fully data-backed today (component search, API lookup, framework-aware recommendations), 3 are partially backed (accessibility guidance, migration assistance, project-aware information) and 3 have zero backing data (usage examples, theme/token lookup, CLI/tooling discovery) — what does v1 actually ship?
- **Repository/Blueprint evidence:** §23 itself says "Potential capabilities" — explicitly not a required list. Blueprint §35 Phase 8's actual objectives are narrower and more concrete: "expose metadata/docs/examples; framework-aware queries; project-aware queries; AI-friendly component discovery" — four objectives, not nine capabilities. Cross-referencing: "expose metadata" ⊇ component search + API lookup (data-backed); "framework-aware queries" = the per-framework filtering already structurally present (data-backed); "AI-friendly component discovery" ⊇ search/lookup (data-backed); "project-aware queries" is the one objective requiring the Fork-2 scoping decision above (narrow, caller-supplied-input version); "docs" and "examples" in §35's phrasing has no backing data (§6 table: no `examples` field exists in the schema at all).
- **Tradeoff:** Shipping tools for the 3 fully-backed capabilities plus a narrowly-scoped project-aware tool satisfies all four of §35's stated Phase 8 objectives using only real data, with zero schema changes and zero fabrication. Attempting "usage examples" or "theme/token lookup" as named, real tools would either return empty results for all 8 components (misleading — implies a capability that returns nothing) or require expanding `ComponentMetadata`'s schema to add an `examples`/`tokens` field, which this task's explicit scope constraints forbid ("Do not expand the component metadata proof set merely for MCP").
- **Recommendation:** v1 ships tools for component search/lookup (including the `guidance`/`accessibility` facets where a given record happens to populate them — read-through, not guaranteed-populated), per-framework API queries, and a narrowly-scoped project/framework-compatibility query (Fork 2's resolution). It explicitly does **not** ship a dedicated "usage examples" or "theme/token lookup" tool, since no real data exists for either — the specification must state this as an explicit non-goal/deferred item, not silently omit it. This is a specification-level scoping decision directly supported by the evidence table in §6; not an unresolved fork.

No candidate fork in this research rose to the level of requiring a stop for a user decision. Fork 1 and Fork 3 are resolved by strong, one-sided evidence (no Blueprint text or repository precedent favors the alternative). Fork 2 and Fork 4 are resolved by direct textual reading of §6/§18/§22's diagrams and §35's actual objective list, respectively — both are specification-scoping decisions within the latitude those sections already grant, not architecture-changing forks.

## 8. What Phase 9 must own instead of MCP

Restated explicitly per this task's scope constraints, cross-checked against Blueprint §24/§25/§26 and GAP-030:

- **Skills** (`@ultimate/ai`, repo-root `skills/`) — "operational AI guidance," versioned and tied to metadata versions, per §24. MCP may be *consumed by* an agent that also has Skills loaded, but MCP itself does not author, package, or version Skills content. `packages/ai` remains `.gitkeep`-only; Phase 8 does not touch it.
- **Generated LLM context** (`llms.txt`, `llms-full.txt`, structured/framework-specific/project context per §25) — explicitly a Phase 9 deliverable ("Generated outputs should not become the primary source of truth" — §25). MCP is a live query interface over metadata, not a static generated-file producer; the two are different mechanisms for related goals, and Phase 8 does not generate these files.
- **AI Context Layers taxonomy** (§26: Platform/Framework/Component/Theme/Project/Task Knowledge) and **agent-instruction-file conventions** — named as Phase 9 objectives ("agent instruction conventions") in §35. Phase 8 exposes component-level facts through MCP tools; it does not define or own the broader AI-context-layer taxonomy or agent-instruction-file conventions that taxonomy implies.
- **AI validation workflows** (§35 Phase 9 objective) — out of Phase 8 scope entirely.

Phase 8 owns exactly the MCP server and its tool surface; nothing about Skills, generated LLM-context files, or agent-instruction conventions is decided or implemented by this phase.

## 9. Summary handoff to specification

The specification must:

- Define `@ultimate/mcp` as a stdio-transport MCP server (Fork 1), packaged with the same conventions already uniform across `component-schema`/`component-metadata`/`cli` (ESM, `tsup`, `vitest --typecheck`, `workspace:*` deps, a `bin` entry point mirroring `@ultimate/cli`'s own shape).
- Define a tools-only v1 surface (Fork 3) covering exactly the capabilities §6's evidence table shows are data-backed: component search/lookup (name/category/description), per-framework API lookup (props/events), read-through of whatever `accessibility`/`guidance` facets a given record happens to populate (no guarantee of non-empty results), and a narrowly-scoped compatibility/framework-awareness query that accepts caller-supplied framework/version input rather than performing its own filesystem project detection (Fork 2) and reads `compatibility-manifest.json` directly rather than depending on `@ultimate/cli`.
- Explicitly state as non-goals/deferred: usage-examples lookup and theme/token lookup (no backing schema field exists for either — Fork 4), any Skills/LLM-context-generation responsibility (§8, Phase 9's), and HTTP transport support (Fork 1, no named consumer).
- State the "read structured metadata only, never parse component source at runtime" boundary (§4) as an explicit, checkable rule every defined tool must pass — mirroring how Phase 7's spec stated its own "orchestrate, don't replace" boundary test.
