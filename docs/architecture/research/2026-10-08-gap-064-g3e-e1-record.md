### Decision requested — D-E1-1 (PrimeNG ImageCompare host)

PrimeNG 21.1.9 puts the root classes on its `p-imagecompare` host element and gives it no `display`; the upstream CSS (`aspect-ratio`, `width: 100%`) needs a block box. The locally recovered pinned PrimeNG showcase `apps/showcase/doc/imagecompare/basic-doc.ts` places it in a flex container (`card flex justify-center`); CSS blockifies a flex item. The source excerpt is retained in the recovered session transcript (tool result before compaction). In our block-container case the PrimeNG oracle collapses to a 17 px line. Ultimate Angular's root is also its host (`u-image-compare`); after a faithful port it would collapse the same way in a block container.

- **(a) Recommended, subject to authorization:** compare Angular ImageCompare in the showcase's canonical setup — the `Sized`/`Rtl` verification stories and their reference cases use a flex wrapper (`display: flex`) on both sides, both frameworks. These are G3-E verification stories, so this is a case-setup correction (no product change). Record as an observation that Ultimate Angular, like PrimeNG, needs a block/flex context after the port (consumer-visible: `MIGRATION.md`).
- **(b)** Keep the block container and retain its measured collapse as the Angular oracle. Record the geometry explicitly; do not label it a match or silently change the oracle.
- **(c)** Keep Ultimate's `display: inline-block` on the Angular root as a retained D5 rule (Ultimate-specific difference, C with reason "renders in any container"), and compare in the flex setup.

A setup change would invalidate the current Angular geometry as a like-for-like before/after baseline. Approval of (a) or (c) must explicitly authorize the corrected-case before-port capture and any affected Ultimate baseline refresh **before** porting. No corrected-case run or story change has occurred. If that exceeds the Plan's iteration allowance, stop for a Plan amendment instead of adding an implicit iteration. ## E1-B1 investigation and E1-V2 V2 result — 2026-10-11

### E1-B1 — evidence and resolution proposal (status: **BLOCKED**, unchanged)

**Question (user):** does the absent upstream token `imagecompare.handle.border.style` mean (1) the mapping should use an existing upstream token, (2) Ultimate needs its own token, or (3) the AC2 assertion's assumption that every referenced key resolves in upstream Aura is invalid?

**Evidence:**

- **The token does not exist in upstream Aura's schema.** In the pinned `@primeuix/themes` 2.0.3 types (`types/imagecompare/index.d.ts`), `ImageCompareTokenSections.Handle` declares `borderColor`, `hoverBorderColor`, `borderWidth` and `borderRadius`. There is no `borderStyle`. The Aura preset (`.vendor-extracted/themes/src/presets/aura/imagecompare/index.ts`) sets `borderWidth: '0'` and `borderColor: 'unset'`, with no style value.
- **Upstream references it once, inconsistently.** In `@primeuix/styles` 2.0.3 (the committed fixture), `.p-imagecompare-slider::-moz-range-thumb` uses `border: dt('imagecompare.handle.border.width') dt('imagecompare.handle.border.style') dt('imagecompare.handle.border.color')`. The parallel `::-webkit-slider-thumb` rule uses the literal `border: dt('imagecompare.handle.border.width') solid dt('imagecompare.handle.border.color')`. Every other `handle.border.*` reference resolves.
- **Prime ships the same reference.** In PrimeNG/PrimeVue the Firefox thumb `border` shorthand contains an undefined custom property. It is therefore invalid at computed-value time and falls back to its initial value (no border). With Aura's `borderWidth: '0'`, the rendered result is the same as the WebKit rule's.
- **Ultimate reproduces it faithfully.** The approved E-1 mapping ports the group text verbatim (fidelity test); the generated `--u-imagecompare-handle-border-style` reference is unresolved for the same reason. The AC2 assertion reports exactly that one variable, and nothing else in any G3-E module.

**Conclusion against the three options:**

- **(1) No existing upstream token** represents a border style for the handle; the only upstream precedent is the WebKit rule's literal `solid`.
- **(2) An Ultimate-defined token** would invent a design token that upstream Aura does not have; no evidence supports a value or a need.
- **(3) The assertion's assumption is invalid for this reference:** AC2 assumes every key referenced by the ported upstream text resolves in upstream Aura, and this one does not resolve upstream either.

**Smallest justified resolution proposal (not applied; needs authorization):**

- **(a) Recommended:** keep the ported text exactly as upstream, and give the AC2 assertion (both `g3e-aura-styles.spec.ts` unit files) one narrow, documented exemption for `--u-imagecompare-handle-border-style`. The reason: a reference that is undefined in upstream Aura, verified absent from the `@primeuix/themes` 2.0.3 schema. This follows the existing in-function `--u-imagecompare-scope-x` exemption pattern. Every other reference stays strictly checked. Required tests after the change: both unit suites (expected: E1-B1 assertions pass), fidelity, and the G3-E regression spec unchanged.
- **(b)** Map the Firefox thumb's style part to the literal `solid`, as the WebKit rule does: a B adaptation that changes the approved E-1 mapping. It needs a corrected record, approval, and a Firefox confirmation of the thumb.

No token value is invented, the assertion is not weakened, and the mapping is not changed until one of these is authorized. **E1-B1 stays BLOCKED**, and the AC2 failure remains outside the allowed AC7 set.
